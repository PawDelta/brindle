4. MCP resilience
-----------------
Driver: .brindle/agents/smoke/resilience.py (stdlib only), run with the candidate's
python -I. It starts `brindle mcp` as a live child process with stdin/stdout pipes, so
requests can be sent over time. The child's stdout is read on a thread, responses are keyed
by id, and stderr is kept. Home: .brindle/agents/smoke/home-resil. config.json is the
user config (~/.brindle/config.json equivalent), which _watch_visuals re-reads every 5 s
(src/brindle/mcp_server.py; #414).

Sequence and results (from the run output):
  initialize                         answered in 0.91 s, no error
  tools/call list_agents (valid)     answered in 0.07 s, "No agents."
  config.json := invalid JSON        (written by the driver)
  wait 7 s (past one 5 s watch tick)
  tools/call list_agents             answered in 0.03 s, "No agents."
  tools/call get_progress            answered in 0.03 s, "Not running as a brindle agent."
  config.json := valid JSON          (restored)
  wait 7 s
  tools/call list_agents             answered in 0.04 s
  burst: 6 concurrent list_agents    all answered, 0.12 to 0.48 s, none errored
  tools/call wait_for_worker (bad id)answered in 0.48 s with isError true:
                                     "Error executing tool wait_for_worker"
Stderr (.brindle/agents/smoke/resil-stderr.log, 351 lines) shows the watch saw the bad file:
  JSONDecodeError: Expecting ...   (the config read at the invalid JSON)
and the bad-id call logged:
  AgentError: no agent 'no-such-worker'
  UnexpectedToolError: Error executing tool wait_for_worker
The server kept answering after both. PASS for "watch survives an invalid config.json and
still answers tools/call".

NOT EXERCISED: a slow tool call run in parallel. The slow candidates all returned at once
without a live worker: wait_on with a future `until` returned immediately ("Not running as
a brindle agent" / no result), and wait_for_worker only blocks on a process-backed worker
(_await_worker returns at once for a non-running agent). Making a real slow call needs a
running worker with tmux and an agent process, which the rules here do not allow. The burst
above shows concurrency only.

Finding (minor, pre-existing as far as this run shows): wait_for_worker with an unknown
agent id returns a tool error after logging a traceback. The server stays responsive, so
it is not a hang, but the unknown-id path raises AgentError instead of returning a message.
I did not check v0.6.3 for the same behaviour.
