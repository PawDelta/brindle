MERGE CONFLICTS IN BRINDLE: INVESTIGATION (2026-11-11)
=====================================================

Scope: read-only. Sources: ~/.brindle/brindle.db (opened with -readonly),
git history of this repo (main, brindle/session-*), and the code on this
branch. No src changes.

Caveat on the data: brindle's events table has no conflict or overlap event
kinds at all, and pipeline_conflicts has no timestamp. So every per-day count
below comes from message text in the inbox table (agent and pipeline
messages). Git cannot count conflicts directly: a conflict shows up only as a
merge commit whose message was preceded by a "conflicts in" pipeline message.

  Product files:
    app/src/screens/Session/GoalPanel.tsx,

    src/brindle/plans.py, src/brindle/pro/shared_docs.py,

  Hot spots are GoalPanel.tsx (2 messages), Sidebar.test.tsx (3), db.py (1),
  and the store files. mcp_server.py did not appear in this window.

The most-repeated collisions are the same few test files, touched by every
feature branch: Sidebar.test.tsx, tests/test_visuals.py, tests/test_daemon_api.py.

Why the coordinator didn't prevent them (ranked below, with code):

(a) Session branches are not checked at all. The coordinator's clash checks
    compare only:
      - declared `files` of running tasks (declared_clash, tasks.py ~L244)
      - changed files of running workers' worktrees (_running_overlap, tasks.py ~L230,
        and conflict_forecast, tasks.py L338)
      - reported-but-unmerged branches (_reported_unmerged, tasks.py ~L509)
    A session integration branch (brindle/session-8, brindle/session-3,
    brindle/session-10) is none of these. Its accumulated diff against main
    is never compared with anything. So a feature branch that merges into
    session-8, or session-8 absorbing main, collides with a diff nobody checks.
    conflict_forecast uses running_tasks only: once a worker reports, it drops
    out, which is exactly when its branch gets merged. Strong gap.

(b) Divergence of session branches from main. Measured now:
    brindle/session-8: 251 commits ahead of origin/main (supervisor's
    figure confirmed). Its first-parent history shows it being used as the
    integration target: 47 to 61 pipeline merges a day into brindle/session-N
    since 11-06. The pipeline refuses to merge into a session branch until it
    has absorbed origin/main, and the sync check (session_sync.py L252-L273)
    then reports the conflicting files. These sync refusals start on 11-06 and
    are the same files the session already changed. Session sync was added on
    11-02 (commits 0f5c9f6c "Keep a session branch synced with origin's
    default branch" and 2aaf809b). It only does its job when a session has
    absorbed main recently, and the sessions here go days without doing so.
    I found no code that warns about, caps or nudges divergence from main.
    session_sync.py reports "behind" and the conflict list, but there is no
    threshold and nothing prompts a PR to main.
    session_sync currently has 17 "synced" rows and 1 "conflict" row. The
    session-8 row records 4094b712 as its upstream sha, which is older than
    main's current tip, so it is not up to date with main.

(c) The overlap warnings are noise, so the signal is lost. The glob matcher
    in tasks.py L59-L80 (_glob_match) uses fnmatch in both directions. fnmatch
    lets `*` cross `/`, so a declared pattern like `src/**` or `app/**`
    matches every file under that tree. Broad globs therefore clash with
    almost anything, and the warning fires on every assign. The warning text
    then says the task is allowed to start with a warning, which 80-95% of
    the 11-06 to 11-10 messages say. Warnings went from about 20-50/day to
    85-230/day. Warnings with no action are ignored, and the one that matters
    (a real collision) is lost among them.
    Note: .brindle/config.json has no `overlap` key, so overlap_mode
    (tasks.py L291) falls back to "block" within a session and "queue" across
    sessions. I did not establish which mode produced each "allowed to start"
    message, so I do not claim the setting is the cause.

(d) Test files are the shared surface. Almost every feature adds tests to the
    same handful of test and UI-test files, and the coordinator checks only
    declared globs, which for tests usually say tests/** (the warning
    "overlaps on tests/** with fab0aafc" from 11-09 is one example). That
    makes every pair of concurrent features collide in tests, so tests
    conflict even when the product code is independent.

(e) Cross-session merges into main are not the driver. Merges into main per
    day fell from 4 to 8 (10-30..11-05) to 0 to 2 (11-06 on); the traffic
    moved into session branches. So "cross-session merges into main" is not
    supported by the data.

(f) conflict_notices rows. They exist (39 rows now) and the table cascades
    on workspace delete (db.py L318). A notice is written only from the
    worker's Stop hook (warn_predicted_conflicts, tasks.py L358), once per
    pair, so a removed workspace drops its notices and the next turn re-warns.
    This adds noise but does not cause collisions. Small.

(g) Hot files: GoalPanel.tsx, db.py, plans.py and the store files show up,
    but only once or twice each. They are a minor cause; the test files
    matter more.

Ranking (most to least important):
  1. Session integration branches diverge from main and are never checked
     (a, b): the largest cause, and the one the coordinator cannot see.
  2. Overlap warnings with broad globs flood the signal (c): explains why the
     warnings don't prevent anything.
  3. Shared test files as the collision surface (d).
  4. Conflict forecast ignores reported-but-unmerged work (a, part): small
     direct gap, but it explains why predicted conflicts never warn at merge.
  5. Hot product files (g) and notice cascade (f): minor.

The overlap logic itself has barely changed since 10-19. The 11-02 session

So the change is in the shape of work, not the coordinator: session-8 and
session-3 are used as integration branches (47 to 61 merges a day into
brindle/session-N since 11-06), plus session sync (11-02) that now refuses
merges until a branch has absorbed main. The coordinator's rules were written for
worker-level collisions in a world where branches were short-lived.


4. PROPOSED FIXES (CONCRETE)
----------------------------

1. Divergence cap for session branches (fixes 1a/1b). Track commits ahead
   of origin/main and days since last sync per session branch. At a
   threshold (e.g. 50 commits or 2 days unsynced) the supervisor is told to
   open a PR to main, and session sync absorbs main before the pipeline
   takes new merges. Implementation point: session_sync.py, next to Drift
   (L50) and the "behind" outcome (L252).

2. Coordinator sees session diffs (fixes 1a). In find_clash
   (inspected_clash / _running_overlap, tasks.py L230-L282), also compare the
   changed files of each other session branch against main
   (`git diff --name-only origin/main...brindle/session-N`), and include
   reported-but-unmerged work in conflict_forecast, not only running_tasks
   (tasks.py L338-L355). This is what would have caught the session-8 / session-3
   overlaps before the merge.

3. Narrow the broad globs (fixes 2). In _glob_match / the assign path, count
   how many repo files a glob matches. A glob matching more than N files (or
   any `src/**`, `app/**`, `tests/**`) is reported as "broad: N files" and
   checked against the changed files of other branches, not against every
   file. Keep the warning only when it names a real shared file. Fixed text:
   one warning per (task, holder, shared files), not per assign.

4. Split the hot test files (fixes 3). Move new feature tests into new
   per-feature modules (the test budget rules already prefer new files for new
   modules) so concurrent features stop editing the same test file. Start
   with tests/test_visuals.py, tests/test_daemon_api.py, and
   Sidebar.test.tsx, the most repeated collisions.

5. Set an explicit `overlap` in .brindle/config.json (e.g. "block") after
   fix 3, so the mode doesn't depend on the default. Verify first which mode
   produced the "allowed to start" messages.

6. Keep conflict notices past workspace removal (minor, fix 5 of ranking).
   Store the warned pair in the merges ledger, not only in the cascading
   conflict_notices table, so a removed workspace doesn't re-warn.

7. Add real telemetry (instrumentation gap). Add `conflict` and `overlap`
   event kinds to the events table and record the file list, so the next
   investigation doesn't have to parse inbox text. Currently the events table
   has no such kinds.


5. ANSWER TO THE SUPERVISOR'S CHECKS (839dd990)
-----------------------------------------------

(a) Did conflicts happen when session branches synced with main or with each
    other? Yes, both. The "origin/main has N commits ... conflicts in" messages
    are the sync-with-main refusals (about 26 from 11-06 to 11-10). The
    "merging brindle/session-N into <feature> conflicts in" messages are
    session-with-session. Both have the same shape: the session branch has
    diverged and touches the files the feature branch also touches.
    I did not reconstruct which exact sync produced each message.
(b) Does anything warn about or limit divergence? No. session_sync reports
    "behind" and the conflict list, but has no cap, no threshold and no PR
    nudge (session_sync.py L252-L273).
(c) Concrete fixes: fixes 1-3 above.
