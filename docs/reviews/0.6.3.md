# brindle 0.6.3 release review

Reviewed: `git diff v0.6.2..origin/main` at `2e7b8a16` (engine `src/brindle`, `app/src`,
`app/src-tauri`, `.github/workflows`), 206 files, about 26,600 added lines.
No product code was changed. Date: 2026-11-10. Second pass the same day, after the
first review of this document asked for the areas it had only skimmed.

Seven findings, most severe first. Three are release blockers in my view (1, 2 and 3).
Each says how it was checked: "measured" means I ran the release code; "read" means
I traced the code and did not run that path.

| # | Severity | Area | Finding |
|---|----------|------|---------|
| 1 | High | Permission checks | A destructive git command behind an unlisted wrapper is no longer seen as git: the force-push deny and the default-branch ask are skipped |
| 2 | High | Worktree removal | A workspace can't be removed at all when the repo and brindle's home are on different volumes |
| 3 | High | Planning docs | The offer to plan a big goal first holds the session's workers, and only the desktop app can answer it |
| 4 | Medium | Stuck workers | Once brindle gives up taking a stuck worker over, its supervisor can never end a turn |
| 5 | Medium | Worktree removal | Every removal re-measures the whole trash N×(N+1) times |
| 6 | Medium | Visuals | Exporting a visual answered with an option and no note fails with a 500 |
| 7 | Medium | Release CI | The workflow's approval moved to a `release-gate` environment that doesn't exist yet |

## 1. High: wrapped git commands bypass the force-push deny and the default-branch ask

`src/brindle/permissions.py:1535-1564` (`_git_invocations`), changed in #376.

In 0.6.2 every word named `git` in a command segment counted as a git invocation.
In 0.6.3 only the segment's first word does, or the command behind a wrapper listed in
`_PLAIN_WRAPPERS` (`permissions.py:3752`). Any other program that runs its arguments
hides the git call from `destructive_git` (`:2583`) and from the push rules, so
`d-git-force` (deny, `:423`) and `d-push-default` (ask) no longer match.

Measured with `permissions.decide()` on the release code, preset rules as seeded:

| Command | autonomous (the default preset) | standard / permissive |
|---|---|---|
| `git push --force origin main` | deny | deny |
| `find . -maxdepth 0 -exec git push --force origin main \;` | **allow** | ask |
| `arch -arm64 git push --force origin main` | **allow** | ask |
| `script -q /dev/null git push --force origin main` | **allow** | ask |
| `xargs git reset --hard`, `xargs git clean -fdx` | **allow** | ask |
| `uv run git push --force origin main` | **allow** | **allow** (preset rule `uv `) |
| `uv run git reset --hard HEAD~3` | **allow** | **allow** |
| `npm exec -- git push --force origin main` | **allow** | **allow** (preset rule `npm `) |
| `uv run git push origin main` (default branch) | **allow** | **allow**, was ask |

With 0.6.2's `_git_invocations` put back into the same code (copied from the diff), the
same probe denies every forced one and asks for the default-branch push.

Failure scenario: a worker on the default Autonomous preset, told by a reviewer to
"reset the branch and push again", runs `uv run git push --force origin main` (or the
`find -exec` form). 0.6.2 denied it; 0.6.3 runs it with no prompt, and the default
branch on the remote is overwritten. Under Standard and Permissive the `uv ` and `npm `
allow rules turn the same command from a deny into an automatic allow. OpenCode's new
"autonomous" mode (nothing of OpenCode's own asks, `opencode.py:337-370`) relies on
these same rules as its only gate.

Still denied (measured): git behind the listed wrappers (`nohup`, `env A=1`, `sudo`,
`command`, and `time`), behind `sh -c '...'` and `eval`, and after `;`, `&&` or
inside `if`. Not seen as git any more (measured): `xargs`, `find -exec`, `setsid`, `arch`,
`script`, `strace`, `uv run`, `npm exec`, `npx -c`; any program outside the wrapper
list behaves the same.

Direction: for deny and ask rules, keep 0.6.2's "any word named git" as the fallback
when the first word is not git and not a known wrapper; the narrower reading is only
safe for allow rules.

## 2. High: a workspace can't be removed when the repo is on another volume than brindle's home

`src/brindle/trash.py:158-159`, `src/brindle/git.py:773-785`,
`src/brindle/workspaces.py:764-767` and `:370`, `src/brindle/pool.py:224,274`.

`git.remove_worktree` no longer runs `git worktree remove`; it moves the checkout into
`<brindle home>/trash` with an exclusive rename, and `trash.put` refuses when the
checkout and the trash are on different devices ("trash is on another volume; original
kept"). Worktrees live under `<repo>/.brindle/worktrees/`, the trash under `~/.brindle`.
0.6.2's fallback for a forced removal (`shutil.rmtree`, then `worktree prune`) was
deleted, so nothing removes the folder.

Failure scenario: the repo is on an external or second disk (`/Volumes/Code/app`), on a
separate Linux partition, bind-mounted into a dev container, or under `/mnt/c` in WSL.
`remove_workspace`, forced or not, ends in "could not remove worktree directory at …:
worktree kept: trash is on another volume". By then the workspace's agents are stopped
and its tmux session is closed (`workspaces.py:750-762`), but the row and the folder
stay, and every later try fails the same way. Worktrees pile up with no way to clear
them from brindle. The same applies where the exclusive rename isn't available
(`trash.py:74-75`, or a filesystem that refuses `renameat2` flags).

What else it takes down on those machines:

- `_reuse_registered` (`workspaces.py:370`, the `try/except` around the removal was
  dropped) and the worktree pool's sweep (`pool.py:274`) now raise where they used to
  carry on: reusing a branch whose old worktree is dead, and the pool's cleanup, fail.
- The MCP `remove_workspace` cancels the queued tasks that depend on the branch and
  records it as removed before it tries the removal (`mcp_server.py:1664-1671`), so a
  removal that then fails has already cancelled them.
- A stuck worker can't be retired, which leads to finding 4.

Checked by reading; I did not run it on a second volume. The device comparison is
explicit and the module's first line says "Cross-device moves fail closed".

Direction: when the trash can't take the checkout, fall back to what 0.6.2 did for a
clean or forced removal (a dirty unforced one is already refused earlier), or keep a
trash folder per volume.

## 3. High: the offer to plan first holds a session's workers, and only the app can answer it

`src/brindle/autopilot.py:764-786` (`consider_plan_offer`), called from `set_goal`
(`:731`) and from every worker spawn (`agents.py:520`); thresholds in
`src/brindle/pro/analysis_brief.py:61-83`; the hold in `src/brindle/plans.py:226-239`
and `src/brindle/tasks.py:946-960`; `assign` queues behind it at
`src/brindle/mcp_server.py:1040-1055`; the only answer is
`POST /v1/goal/plan-offer` (`src/brindle/daemon/routes_actions.py:1154-1161`).

New in 0.6.3: a goal with 4 or more milestones, 2 or more repos, 3 or more workers
assigned, or 3 milestones and a word like "refactor" or "migrate" opens an offer,
"This looks big: plan it first?". While it is open, every `assign` from that session is
queued and nothing starts it (`tasks.plan_holds`); the task sweep leaves it queued. The
offer is made whenever the visuals setting is on, which is the default
(`config.py:566`, #380), whether or not the desktop app is there to show it. The only
callers of the answering route are the app's Inbox card (`app/src/api/client.ts`,
`InboxScreen.tsx`); the CLI, the terminal sidebar and the MCP tools have none. A
planning doc is the same: `plans.decide` takes the person's verdict only through the
daemon route.

The repo's own test shows the hold (`tests/test_plans.py:286-293`): after a
4-milestone `set_goal`, `assign` leaves the task pending, `tasks.sweep` starts
nothing, and only the POST releases it. I found no other release by searching every
use of `plan_offer`, `answer_offer` and `plan-offer` in `src/brindle`.

Failure scenario: someone runs brindle from a terminal, with no desktop app. The
supervisor sets a goal with four milestones, or assigns its third worker. From then on
each `assign` answers "Queued task … behind brindle's offer to plan this goal first:
it starts once the person chooses not to, or approves the plan". The supervisor tells
the person, who has nowhere to say yes or no. The session makes no further progress
unless they find `BRINDLE_VISUALS=0` or the `visuals_enabled` setting. 0.6.2 had no
such hold.

Direction: make the offer only where something can answer it (a connected app), or
give the terminal an answer (a CLI command, or the supervisor's `need_user` path), or
let an unanswered offer lapse after a while.

## 4. Medium: once brindle gives up on a stuck worker, its supervisor can never end a turn

`src/brindle/open_items.py:137-151` (`stop_block`), `:101-102` (`_takeover_due`),
`:127-134` (`_cannot_close`), `:296-303` (`_give_up`); called first in the Stop hook at
`src/brindle/autopilot.py:2390-2395`.

A worker that stops without reporting opens an item, and while it is open the
supervisor's Stop hook answers "block": "You can't end your turn with this open". The
block has no cap of its own (the ordinary nudge beside it stops after `MAX_NUDGES` and
backs off; this returns before any of that, and before the usage-limit and
waiting-on-the-person checks). It is meant to lift after an hour, when brindle takes
the worker over. But when the takeover can't be done, `_give_up` sets the item's level
to `GAVE_UP`, and `_takeover_due` is false at that level for good, so the block comes
back on every stop.

Measured with `open_items.stop_block` on the release code, a worker whose process is
gone and whose worktree still exists: a newly opened item blocks now and lets the stop
through two hours on; after `_give_up` it blocks now, two hours on and two days on.

The supervisor has three ways to close the item, and for this worker each can fail:
`send_message` is refused ("agent … is not running"), `requeue` runs the same takeover
and gives up again, and `remove_workspace` fails wherever removal fails (finding 2, a
worktree in use, a failed teardown without force).

Failure scenario: on a machine where the repo is on another volume, a worker's CLI
dies mid-task. An hour later the takeover fails at "removing its worktree failed". From
then on every time the supervisor tries to end its turn it is sent back with the same
instruction, cannot satisfy it, and tries again: an unattended session spends tokens
in a loop until the person interrupts it.

Direction: give this block the same cap and back-off as the nudge, and let an item at
`GAVE_UP` stop blocking once the supervisor has been told (it already has been, once).

## 5. Medium: each removal re-measures the whole trash N×(N+1) times

`src/brindle/trash.py:313-327` (`retain`), `:45-59` (`entries`), called from
`src/brindle/git.py:782` after every removal and from `disk.retain`.

`entries()` walks every trashed checkout to size it (`disk.size_of`, a full `scandir`
walk, not cached). `retain()` calls it once for its loop and once more per entry, under
the trash lock.

Measured on the release code with empty entries and nothing to remove: 5 entries, 30
tree walks; 15 entries, 240; 35 entries, 1,260.

Failure scenario: trashed checkouts are kept 30 days or until 10 GB. A person whose
sessions remove a few workers a day has dozens of entries within a week, each a full
checkout with its `.venv` or `node_modules`. Each `remove_workspace` (and each merge
that removes its workspace) then walks all of them dozens of times before it returns,
holding the trash lock, inside the daemon or the MCP call. Removal gets slower every
day until the cap starts pruning. Nobody has had a trash older than the staff builds,
so this hasn't shown yet.

Direction: read the entries once per `retain()`, and store each entry's size in its
`entry.json` when it is trashed.

## 6. Medium: exporting a visual answered without a note fails

`src/brindle/visual_export.py:181-182` (`sanitise`), with `src/brindle/visuals.py:402`.

`visuals.answer` stores `{"option": ..., "note": None, ...}` when the person picks an
option and types nothing. `sanitise` then calls `html.escape(answer["note"])`, which
raises `AttributeError` on `None`; the route answers 500 "internal".

Measured: `visual_export.sanitise("<p>hello</p>", {"option": "a", "note": None, ...})`
raises `AttributeError("'NoneType' object has no attribute 'replace'")`. With a note,
or with a note and no option, it works.

Failure scenario: the person answers a visual by clicking an option and Send (the most
common answer), opens it again and exports it: the download or the Google Drive export
fails, every time, until a new revision clears the answer.

## 7. Medium: the release workflow's approval now names an environment that isn't there

`.github/workflows/app-release.yml:139-165` (`release-gate`, `environment: release-gate`),
comments at `:45` and `:141`; `.github/workflows/app-feed-rollback.yml:56-59,86-90`.

The workflow moved the owner's approval from `desktop-release` (which holds the Apple,
Tauri, Azure and AWS credentials) to a new secret-free `release-gate` environment, and
its comments say `desktop-release` now "has no required reviewers".

Checked against the repository's settings today (`gh api .../environments`): there are
three environments, `desktop-release` (required reviewers and a tag policy),
`desktop-staff-release` and `pypi`. There is no `release-gate`.

What that means for the 0.6.3 tag:

- As settings stand, nothing is weaker: every job that reads the secrets still waits
  for a `desktop-release` approval. But the new gate job references an environment
  GitHub will create on first use with no protection rules, so it passes at once and
  its summary line reads "approved by nobody recorded". The one-approval flow the
  workflow describes is not what will happen.
- The risk is the next step. If `desktop-release`'s reviewers are removed as the
  comments describe before `release-gate` exists with required reviewers and an
  `app-v*`-only policy, a tag push builds, signs and publishes with no approval at all.
- After the move, the approval is enforced by the workflow file at the tagged commit
  (`needs: release-gate`), not by the environment that holds the secrets. A tag on a
  commit whose workflow drops that `needs` would reach the secrets unapproved. What
  stands in the way is the tag ruleset "app release tags" (create, update and delete of
  `app-v*` limited to the admin role), which I confirmed is active. Worth deciding on
  purpose whether that is enough before taking the reviewers off `desktop-release`.

Direction: create `release-gate` (required reviewers, `app-v*` tags only) before
tagging 0.6.3, and only then decide about `desktop-release`'s reviewers.

## Areas with no finding

Each line says what was read and how far.

**Security**

- **Keychain listing** (`keystore.listed_reads`, `keystore.py:102-129, 281-331`; read in
  full). The listing is `security dump-keychain` without `-d`: attributes only, no
  secret. Its output is never logged, and a `TimeoutExpired` that would carry partial
  output is replaced by a plain `CredentialError`. A listing with any stderr, a
  non-zero exit or a record the parser doesn't fully understand is not trusted and
  each lookup reads its item as before. Lock order is the same in `load`, `save` and
  `delete` (item, then listing). One behaviour change: inside a resume, a key saved by
  another process can read as missing for up to the listing's 30 seconds; the per-item
  cache already had the same window for a cached miss.
- **Secrets in logs and errors** (`github_connect.py`, `mac_keychain.py`,
  `debuglog.py`, `attachments.py`, the GitHub routes; read in full). The token is
  popped from the request body, errors carry codes and fixed text, the catch-all drops
  the traceback. Recovery timing lines carry ids, counts and seconds. Attachment errors
  are rewritten without paths. `/v1/github/credential` gives the token to any process
  on the Unix socket without the bearer token; that is the documented design (git's
  helper in a pane must be able to ask), and the host and scheme check is exact.
- **Rest of the permission checker** (`permissions.py`; the whole diff read, the allow
  paths probed). Measured on the Standard preset: a quoted or escaped substitution
  spelling (`echo '$(touch x)'`, `echo "\$(touch x)"`) is allowed as read-only, and
  every live one I tried is not (`"a'$(…)'b"`, `"\\$(…)"`, a backtick in double
  quotes, one after a closed single-quoted word). The new `git grep` allow refuses
  `--no-index`, `-O`, `--open-files-in-pager`, a `-C` outside the session and a
  revision before `--`. The new wrappers (`sudo`, `doas`, `flock`, `chroot`,
  `unbuffer`) are only used to widen denies. The credential-scan additions (dotglob,
  arrays, pieces of a store's path, `git credential fill`) only add denies.
- **OpenCode's autonomous mode** (`opencode.py`, `agents.permission_request_decision`;
  read in full). Every path I traced fails closed: a hook that didn't exit cleanly, an
  answer that isn't JSON, a request brindle can't read, an ask, an exception, the
  rules turned off after launch. Its strength is that of the rules themselves (see
  finding 1).
- **Visual sandbox** (`visual_scheme.rs` read in full, all three platform blockers;
  `lib.rs`; `capabilities/default.json`). Commands are refused unless the asking
  webview is `main`, and the capability names the `main` webview, not the window. The
  scheme serves a page only to the webview bound to that id and revision. Navigation
  is limited to the page's own URL, new windows and downloads are denied, WebRTC is
  removed before page script runs, and each platform arms a deny-by-default request
  blocker before the page loads and loads nothing when it can't (macOS content rule
  list and the preconnect switch through WebKit's private feature list; Windows
  resource filter plus resolver and proxy switches; WebKitGTK filter store). The CI
  job runs the hostile probes on all three. I did not run them myself.
- **Attachments** (`attachments.py`, `routes_actions.attach_agent`, the Rust clipboard
  and WSL path commands; read in full). Source files are opened by descriptor with no
  symlink in any component, credential stores are refused on both the given and the
  rewritten path, and an answer's attachments must resolve inside the receiving
  agent's own attachments folder.
- **Visuals and plans, engine side** (`visuals.py`, `visual_offers.py`, `plans.py`,
  `routes_visuals.py`, `visual_export.py`; read in full). Ids are checked before they
  reach a path, an answer is claimed in the row before it is delivered, a plan's
  verdict is one transaction and only the daemon route may give it, and an agent's
  `approve_plan` on a plan id is refused. Typed words are kept at most 30 minutes and
  not at all when they look like a secret.

**Restart recovery and delivery**

- **Restart recovery** (`lifecycle.py`, `agents.resume`, `settle_panes`,
  `panes_match`, `tmux.agent_panes`, `signin_pause.py`, `/v1/recovery/*`; read in
  full). The record stays on disk until tmux confirms a session; stop waits for
  launches under way; per-resume credentials go through a context variable and the
  start's environment snapshot. The two recovery routes take only a session id, sit
  behind the Guard, and write a fixed file. See the notes for two things I could not
  turn into a failure.
- **Message delivery and reports** (`agents.py` pane delivery, `wake.py`, the report
  outbox and marks in `db.py`; the whole diff read). Each step is claimed in the
  database before the outside action and released on failure, and a mark whose
  message is gone no longer holds the queue. I traced the main paths (idle paste,
  mid-turn paste, a stopped delivery resumed, a waiter that dies holding mail, a
  report repeated) and did not enumerate every interleaving of hooks with a paste in
  flight.
- **Pipeline, tasks, fair share, autopilot, cull** (`pipeline.py`, `tasks.py`,
  `fair_share.py`, `autopilot.py`, `cull.py`, `open_items.py`, `mcp_server.py`; the
  whole diffs read, `open_items.py` and `fair_share.py` in full). Beyond findings 3
  and 4: a dead reviewer is replaced once under the dispatch lock; the tests-only
  waiver checks the reviewer's claim against the changed files and blocks on doubt;
  the machine-wide worker limit decides again under its lock as the slot is claimed,
  and a task it holds back is picked up by the sweep.
- **Database** (`db.py`; schema, migrations and the new methods read). New features
  get their own tables; the added columns are on tables new in this release or guarded
  by a column check; the one `DROP COLUMN` only runs for a column no release had.

**App**

- **Stale-response handling** (`App.tsx` panes gate, `sync.ts`, `store.ts`,
  `useVisuals.ts`, `VisualReader.tsx`, `PlanReader.tsx`, `NativeFrame.tsx`,
  `OfferChip.tsx`, `VisualsSetting.tsx`, `GithubConnect.tsx`, `ExportMenu.tsx`,
  `KeptVisuals.tsx`, `PtyTerminal.tsx`, `ProviderSurface.tsx`, `SessionScreen.tsx`,
  `InboxScreen.tsx`, `ReconnectOverlay.tsx`; read in full or as whole diffs). The panes
  gate re-checks the daemon's pid, connection generation and lifecycle version around
  every awaited read and has a 30 second deadline; `sync.ts` drops a snapshot older
  than one applied meanwhile and reads again (one dropped after a close is refetched
  because the event marks the store stale). Every reader and form I read guards a late
  answer by a sequence number, a key for the revision on screen, or an "active" flag;
  the plan reader only ever moves forward (a newer revision, or this one decided).
- **Sidebar, Settings, goal panel, walkthrough** (`Sidebar.tsx`, `SettingsRail.tsx`,
  `routes.ts`, `SettingsScreen.tsx`, `GoalPanel.tsx`, `Walkthrough.tsx`). I read every
  changed line that calls the daemon, navigates, sets a timer or registers a listener,
  and the first two thirds of the goal panel's diff; the rest of these diffs is layout
  and styling, which I did not read line by line. The sidebar's changes are navigation
  only; the goal panel's fetch keeps its newest-answer guard.

**Rust shell and CI**

- `daemon.rs`, `startup.rs`, `pty_view.rs`, `wsl.rs` (read as whole diffs): the idle
  launchd job cleanup re-reads each job before removing it; startup timings are fixed
  labels written only for a confirmed staff account; the WSL path conversion passes
  the path as an argument, never as shell text, and refuses another distribution's
  share.
- `app.yml`, `app-release.yml`, `app-feed-rollback.yml` (read as whole diffs): beyond
  finding 7, the Intel build now cross-builds on Apple Silicon with an architecture
  check on every bundled binary, and the stapled app is verified inside both the
  updater bundle and the DMG before anything is published.

## Notes: looked wrong, not confirmed

- `tmux.agent_panes` (`tmux.py:441-455`) returns an empty list for any non-zero exit of
  `list-panes`, not only "no server"; `settle_panes` (`agents.py:1890`) would then mark
  running agents paused. A server that doesn't answer raises instead, and I found no
  case where `list-panes` fails while `new-window` works, so no duplicate launch.
- A session whose resume succeeds but whose panes never match (`panes_match`,
  `agents.py:1926`) stays on the record, and on the third start
  (`lifecycle.py:622-628`) it is left paused, not brought back. I found no ordinary
  state that keeps the panes from matching after a good resume.
- `pipeline.is_test_path` (`pipeline.py`, the tests-only waiver) counts any file under
  a folder named `spec`, `specs`, `test` or `tests` as test code. A repo that keeps
  product text or code in such a folder could have a finding on it waived past the
  review rounds. Not a problem in this repo.
- `NativeFrame.tsx` listens for a visual's `message`, `loaded` and `failed` events but
  not `visual:blocked`, which `visual_scheme.rs` describes as marking the visual
  failed. A denied navigation is still denied; the reader just isn't told.

## What was run

No test suite. Only probe scripts of mine against the release code, each with a
temporary brindle home: the permission checker's answers per preset (findings 1 and
the read-only allow), the trash's tree walks (5), `sanitise` (6), `stop_block` (4).
Three read-only `gh api` calls for finding 7. The probes are not committed.
