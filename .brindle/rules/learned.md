Full coverage is not a goal. A new feature needs a test proving its main path
works; add a failure-path test only when that path matters. A bug fix needs one
regression test that fails on the base and passes after the fix. Refactors,
renames, docs, config, wording and pure glue need no new tests.
- Extend an existing test or parametrize table first. Never test wording,
  constants, defaults, enum values, entry-point registration or mock arguments.
- Every added test or row must catch a distinct bug. Missing feature or regression
  tests and added tests with no distinct bug are blockers.
- scripts/check_new_tests.py checks for unique coverage. Use
  `@pytest.mark.variant("why")` for a deliberate input variant that catches a
  distinct bug without adding coverage.
- Use database rows and fakes. Test functions directly, avoid network calls and
  drive events with a fake clock. Keep at most one end-to-end test per feature.
- Aim for under one second per test; the call-phase limit is 10 seconds.
  Mark a necessary slow test `@pytest.mark.slow("why")`. Share expensive setup
  in a module-scoped fixture and copy it per test.
- When a lookup takes an optional filter (such as a profile), treat None as 'no filter' only when the caller truly means any; never let a missing value match a live resource that belongs to a different identity. When an action can be triggered twice, make the second trigger check for and respect existing in-flight work instead of cancelling or replacing it, and cover that path with a test that runs the real dispatch code rather than a mock. (learned 2026-10-13 from 4 reviews of developer-sonnet work: Lookup ignores caller's filter and races on detached work; rule 8967a6e2)
- Before changing code for a reported bug, write a test that reproduces the reported symptom and fails on the unmodified code. Fix the root cause in the source, then confirm that test passes. A test that already passes before the change is not evidence of a fix. (learned 2026-10-13 from 3 reviews of developer-codex-heavy work: Bug fix not reproduced or root-caused; rule 634c00cd)

- When awaiting asynchronous responses in a UI component, capture the state at request initiation and validate it before updating the DOM or state. If the state has changed during the wait, discard the stale response to prevent overwriting incorrect data. (learned 2026-10-30 from 9 reviews of developer-heavy work: Stale Response Handling in Web Chat; rule 58312e78)
- When a policy resolution returns a denied decision, ensure it is propagated upward instead of silently falling back to a default or less restrictive policy. This prevents unauthorized access through misconfigured or missing policies. (learned 2026-10-30 from 7 reviews of developer-heavy work: Managed-device resolver drops denied member policy; rule 2bbd4c30)
- When implementing failure-safe mutations, ensure that the original content is preserved until the replacement is fully written and committed. Use atomic write patterns that prevent data loss on write failures, such as writing to a temporary file first and then moving it into place. (learned 2026-10-30 from 5 reviews of developer-heavy work: Failure-Safe Mutation Incomplete; rule 43fdb4cd)
- When handling credential errors, ensure that sensitive data such as API keys or secrets are never exposed in error messages, logs, or responses. Sanitize error paths to prevent secret leakage. (learned 2026-10-30 from 3 reviews of developer-heavy work: Secret Exposure in Credential Error; rule 1150b51d)

- When checking test coverage for production changes, do not treat deleted test files as valid coverage. Track added/modified test paths separately and require at least one test with new content to pass validation. (learned 2026-10-30 from 3 reviews of developer-heavy work: Test Deletion Allows Bypass of Coverage; rule eb5d2120)
- In patch parsing, only recognize file headers (`--- ` or `+++ `) before entering a hunk. Ensure that body lines starting with `--- ` are not mistaken for file headers and cause misattribution in overlap scoring. (learned 2026-10-30 from 3 reviews of developer-heavy work: Diff Parser Misinterprets Hunk Content; rule a170d30e)
- When reducing or consolidating tests, do not delete a test that guards a failure path. Each protected scenario, such as a launch failure converting to its error code, must still be exercised by a retained test, and coverage should confirm this before anything is removed. (learned 2026-11-03 from 10 reviews of developer-sonnet work: Regression coverage removed while trimming tests; rule 45e97b5c)
- When using ThreadPoolExecutor in asynchronous operations, ensure that request context such as deadline and disconnect tokens are properly propagated to each submitted task. Copy the request context separately for each task and audit other request-owned pools to prevent loss of critical session information. (learned 2026-11-03 from 3 reviews of developer-heavy work: Request Context Lost in ThreadPoolExecutor; rule ff6a01f8)
- Immediately before each destructive action (kill, stop, delete, reap), re-read the ownership, attachment, activity, and dirty-worktree state and skip the candidate if it changed since planning. Apply every safety guard to every destructive path, not only the one that was patched, and add a deterministic regression test that changes state between planning and acting. (learned 2026-11-06 from 3 reviews of developer-heavy work: Destructive action on stale or unguarded state; rule 801c9de5)
- Do not assert exact message or label wording in tests unless the task requires that copy. Assert a stable rendered state (a data-state attribute, an error role, or the branch that was taken) that the same code path sets, and keep the behavior check, such as an HTTP 500 regression, in place. (learned 2026-11-08 from 3 reviews of developer-sonnet work: Tests assert exact user-facing copy; rule 87c375d0)
- A regression test must correctly detect the issue it is meant to prevent. When using frame or observer callbacks, ensure assertions are executed after React commits updates and schedules additional frames, using flushed act() boundaries to capture all side effects. (learned 2026-11-08 from 3 reviews of developer-haiku work: Regression Test Ineffective; rule 51af2bc2)
- Before a doc states what the product enforces, what a statistic measures, or what an installer does, check it against the code and the guide, and use the same scope and denominator as the source (review events, not distinct branches). Qualify any limit that only some providers enforce, and describe per-platform install behavior as the installer script actually does it. (learned 2026-11-08 from 5 reviews of developer-heavy work: Docs claims stronger than their source; rule 1946ec21)
- When a request hands out or starts work that its reply promises, commit that state only after the transport confirms the response was written.
