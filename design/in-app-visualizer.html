1 · where visuals live

Visuals: the pages agents draw for you, opened in the app

When a decision is hard to read in a terminal (three release flows, two wordings of a rule, a merge order), the agent publishes a visual: an HTML page that belongs to its session. You read it, pick an option inside it, and the answer goes back to the agent as a message. Today these pages go out as claude.ai artifacts; this keeps the internal ones in brindle.

4 · planning docs for large requests

Before a big fan-out, the supervisor writes a plan and argues with it

Hand a supervisor something large and, before it starts any worker, it drafts a short planning doc: the goal, how it would split the work, the decisions that shape it with the alternatives it weighed and its own challenge to each, what's hard to undo, and what it doesn't know. It opens as a visual. You read it like a document, answer and comment where you have something to say, then approve or redirect. Workers start only after that. Small tasks never see one.

offered when the request is large

  • It would start three or more workers, or touch more than one repo
  • A step is hard to undo: a migration, a public API, a release, a deletion
  • The goal leaves real choices open (where state lives, what to cut)
  • You asked for one: “plan this first”

skipped and it goes straight out

  • One worker, a clear finish line
  • A bug with a reproducing test, a rename, docs
  • You said “just do it”, or the repo turns plans off
The supervisor offers, it doesn't insist. “Skip the plan” in the chat starts the work anyway; a plan is never more than a page.

5 · architecture sketch

One MCP tool, a store under the session, a sandboxed frame, a message back

Agents already reach brindle through its MCP server, and answers already reach agents as delivered messages. A visual adds one tool, one table, one route for files and one for answers; the app adds a place and a frame.

new piecesuntrusted: the agent's HTMLtrusted: brindle's own chromethe answer's path back

The tool

publish_visual(
  title: str,
  html: str | path: str,      # one of; a file in the worktree
  session: str = "mine",     # default: the caller's root
  question: str | None,
  options: [{id, label, detail}] | None,
  replaces: str | None,       # new rev; old goes stale
) -> {id, rev, link: "brindle://visual/v_8f2c"}

Also list_visuals(session) for an agent to find its own. No polling for answers: they arrive as a delivered message, like a supervisor's.

Plans: propose_plan(markdown, decisions, split). brindle renders the markdown itself (trusted, no frame), so picks and comments anchor to its sections. While it waits, the session's assign calls queue behind it, as with depends_on; approve and redirect reuse approve_plan's approved / feedback shape, from the person to the supervisor.

Rendering

  • Served by the daemon on its own scheme, brindle-visual://, never from the app's origin, with a CSP header: default-src 'none'; script-src/style-src 'unsafe-inline'; img-src data: blob:.
  • <iframe sandbox="allow-scripts"> without allow-same-origin, forms, popups, modals or top navigation: an opaque origin with no storage.
  • CSP and the sandbox are not enough on their own: a sandboxed frame may still navigate itself (location.href = "https://…?d=…", a meta refresh, a link it clicks), and default-src doesn't govern that, nor WebRTC. So the host denies by default: the webview's navigation and request hooks (Tauri's protocol handler and on_navigation; WebView2 NavigationStarting / WebResourceRequested; WebKitGTK decide-policy) let a visual frame load only brindle-visual://<id>/r<n> and its own data: / blob: URLs. Every other navigation, subresource and redirect, a protocol-handler redirect included, is refused, and the attempt marks the visual failed. RTCPeerConnection is removed before the page's script runs.
  • Proved before it's built on: a suite of hostile probe pages (self-navigation, meta refresh, anchor and window.open, a redirecting brindle-visual URL, CSS / image / font URLs, prefetch and DNS-prefetch hints, WebSocket, EventSource, beacon, WebRTC ICE) runs in each shipped webview (macOS WKWebView, Windows WebView2, Linux WebKitGTK) against a local listener that must see zero requests. It stays as a CI test for the shell.
  • brindle prepends its token sheet (--canvas, --ink, …) and sends the theme on change, so a page written against the tokens matches the app in light and dark.
  • Only the active tab is mounted; hidden ones unload.

Answers and retention

  • The frame's only channel is postMessage({type:"choice", option}). The host checks the source window and that the id is one of the tool call's options, then highlights it. Nothing is sent until you click Send.
  • The engine records the answer, resolves the Inbox item and delivers Chose B · Gate on CI plus your note, quoted as yours. No text from the page reaches the agent.
  • Kept with the session; read-only for 30 days after it closes, then pruned with its worktree. 20 revisions per visual; decided ones archived from the list, not deleted.
