Plan · anonymous usage counts

Counting the people who never sign in

PyPI says about 1,200 downloads a week, and nearly all of them are mirrors, scanners and our own CI. The desktop update feed gets 8 to 29 hits a day, but nothing ties a hit to an install. This plan adds two numbers we can trust, first runs and weekly active installs, from the CLI and the app. It does that without an install id ever reaching our servers.

Written 2026-11-06 Engine work: this repo · Server and console: pawdelta-web Branch docs/usage-counts-plan Background: brindle-usage.html (read Nov 6)

This breaks a public promise. The privacy page says the CLI without an account “makes no requests to PawDelta: no telemetry and no analytics”. The security page and the README say the same, and the privacy page says the app's update check “carries no account or install identifier”. Nothing here ships until those pages are rewritten and a lawyer has read the EU section (§10).

01 · The short answer

A weekly anonymous count, opt-out, with no install id

Recommended
  1. A separate weekly ping, not the update check. The update check should keep doing one job. If turning off analytics also turned off updates, people would trade security fixes for privacy (§11 A).
  2. No install id leaves the machine. This goes further than the brief's “random id, hashed server-side”. The client sends the week it was first counted (its cohort). It reserves each week locally before sending, so a lost request means one week too few, never one too many. The server then only adds to counters. That is enough for installs, weekly active and retention by cohort, and nothing stored on our side identifies a machine (§3, §4).
  3. On by default, with a notice first. Nothing is sent until the notice has been shown on a terminal or in the app, and never in the same run that showed it. The consent policy comes from the release itself plus a static policy file that can only make it stricter. That file is read before any count is sent, and if it can't be read, nothing is sent. Every surface has an off switch: a setting, BRINDLE_TELEMETRY=off, DO_NOT_TRACK=1, and brindle telemetry off (§6, §7, §10).
  4. CI, dev checkouts and air-gap mode send nothing. The app's bundled engine is counted, even though it is installed from a local wheel. Our own CI is excluded twice, once by detection and once by an explicit variable. Staff machines send a ping marked internal, which the console keeps out of every total (§5).
  5. Only counters are kept: 24 months, broken down one dimension at a time. No row describes one machine in full (§8).
  6. Server first, then clients. The endpoint, counters and console go live before any client sends. Clients ship after 0.6.3, with a kill switch the server can flip (§13).

03 · Exactly what is sent

One small JSON body, every value from a fixed list

// POST https://pawdelta.com/brindle/… (one fixed path, chosen with the server work)
// body ≤ 1 KB, no query string, no cookies, no auth header
{
  "v": 1,
  "event": "active",         // "first_run" once per surface, then "active"
  "surface": "cli",           // "cli" | "app"
  "engine": "0.6.4",
  "app": null,                // the app's version when surface is "app"
  "os": "macos",              // macos | linux | wsl | windows
  "arch": "arm64",            // arm64 | x86_64 | other
  "channel": "uv-tool",       // app | uv-tool | pipx | pip | script | other
  "providers": ["claude", "codex"],
                                // CLI types detected, from a fixed list; others → "other"
  "signed_in": false,         // is a brindle account signed in on this machine
  "cohort": "2026-W47",       // the week this machine was first counted; "before" for older installs
  "last_week": "2026-W47",    // the previous reserved week, or null: new vs returning only
  "machine": true,            // first week reserved on this machine, by either surface
  "internal": false           // a PawDelta staff account is signed in
}

The client works out week labels itself, as ISO weeks in the console's zone (America/New_York through zoneinfo, with a fixed UTC−5 fallback), so its weeks line up with the site counters. The server counts a ping under the week it receives it in. A client week that disagrees by more than one (a wrong clock) is counted under the server's week, with its cohort folded to other. The server replies with an empty body, or {"stop": true} to switch pings off.

Never sent, and never derived on the server

  • an install or machine id
  • account id or email
  • org
  • IP address (seen in memory only)
  • hostname or username
  • file paths
  • repo names or hashes
  • branch names
  • prompts or task text
  • profile names
  • model names
  • provider accounts or keys
  • locale or timezone
  • country (no geo-IP lookup)
  • error messages
  • anything about sessions or agents

Why no id, when the brief suggested one. An id is useful for two things: removing duplicate pings and following one install over time. The client does the first itself. It reserves the week under a lock before sending, so it never sends twice, and a lost request is an undercount (§4). The server can't remove duplicates, and doesn't need to. The cohort label does the second in aggregate: “of the installs first counted in W47, how many were active in W50” is a sum of counters. With no id there is nothing to rotate or hash, nothing to delete on request, and nothing a leaked table could join to an account.

What it costs. A copied ~/.brindle (a dotfiles sync, a container image, a restored backup on a new Mac) would carry its old cohort, count as a second install and look like it “came back” at once. Mitigation, local only: usage.json keeps a hash of the hostname and home path, which is never sent. If it no longer matches, the state counts as copied and starts fresh, with a new notice and a new cohort. That catches containers and synced dotfiles. What it can't catch is a copy onto a machine with the same hostname and home path, such as a VM clone. That case stays a known overcount, and the console footnote says so.

Every field earns a console view

  • event, cohort, last_week: installs, weekly active, the retention triangle, and new versus returning installs. last_week doesn't remove duplicates; reservation on the client does that.
  • engine, app: version adoption, and how fast a release reaches people.
  • os, arch: OS mix. It answers the Intel-on-Apple-Silicon and Windows questions with numbers.
  • channel: whether people arrive by the install script, uv, pip or the app. The install script writes a one-word marker so script can be told apart from uv-tool.
  • providers: which agent CLIs real installs use. Today we only know this for accounts.
  • signed_in: the share of active installs that never sign in, which is the blind spot itself.
04 · How often, and when

At most one attempt a week per surface, about 52 a year

  1. First interactive runThe notice is printed on stderr in a TTY, or shown on the app's first-run screen, and recorded as notice_shown. Nothing is sent and nothing is fetched yet.
  2. Next run (CLI), or leaving the first-run screen (app): policy firstThe client reads the static policy file, if its cached copy is older than 7 days (§10). If the policy says consent applies to this machine, it asks, and goes no further without a yes. If the file can't be read and there's no fresh copy, nothing is sent this run.
  3. Then the first countUnder the lock, the client writes the week into usage.json as reserved and sets the cohort, then sends first_run for that surface. The person has had one chance to switch it off.
  4. First use in each later weekThe same order: check the policy, reserve the week, then send one active ping from a background thread. The first reservation of the week from either surface sets machine: true.
  5. App left open for daysThe daemon the app started checks every few hours whether this week is reserved yet. One attempt per week still holds.
  6. Offline, the server is down, or the reply is lostThe client gives up after 2 seconds. The week stays reserved, so it is never sent again. That is a deliberate choice: a lost request is one week too few, and the server could never tell a repeat from a second install. Nothing is queued.

Where the call lives

  • A new src/brindle/usage_counts.py holds the gates, the policy read, the reservation, the payload, a non-blocking flock (as in updates.py), a daemon thread, and a function that never raises. (usage.py is taken: it sums transcript tokens.)
  • CLI: called next to updates.newer_version(refresh=True) at session launch, and from other interactive commands through the Typer callback. The surface is cli.
  • App: the engine daemon the app started sends with surface app and the app version it already learns (debuglog.note_app_version). There's no ping code in Rust or TypeScript, which keeps one implementation and one place for the off switch.
  • Exit paths: the thread is a daemon thread, so a short command never waits on the network.

There's no daily ping. Weekly active is what was asked for, and a daily ping would be seven times the traffic for a number we wouldn't read.

06 · Turning it off

One setting, read by every surface, plus two environment variables

Setting

"telemetry": false in ~/.brindle/config.json. The CLI, the daemon and the app all read this one key. The app's Settings › Privacy switch writes it.

Environment

BRINDLE_TELEMETRY=off (also 0, false or no), and the cross-tool convention DO_NOT_TRACK=1. Either one wins over the setting. BRINDLE_NO_UPDATE_CHECK does not stop the ping: updates and counting are separate switches.

Command

brindle telemetry          # on/off and why
brindle telemetry off
brindle telemetry on
brindle telemetry show     # the exact JSON
                           # the next ping sends

brindle doctor gets one line: “Usage counts: on (off with brindle telemetry off)”, or which switch turned them off. Turning it off also deletes ~/.brindle/usage.json, so turning it back on later starts a new cohort. There's nothing to delete on the server, because nothing there belongs to one machine.

10 · EU and consent

Opt-out everywhere, built so a switch can make Europe opt-in

Not legal advice. This is an engineering reading meant to steer the design. A lawyer must sign off before release; the privacy page already carries LEGAL REVIEW markers for transfers and logs.

GDPR Fits legitimate interest

What we store is anonymous aggregates with no identifier, so it is outside GDPR once written. The personal data is the brief processing of the IP address while the request is handled, which already happens for every site visit. Legitimate interest (Art. 6(1)(f)) covers counting adoption of a product the person chose to install, when it is disclosed up front and easy to refuse. Not storing an id is what makes this argument hold: a stable id, even hashed, would be pseudonymous personal data. That would bring access and deletion requests, and the case gets weaker.

ePrivacy, Art. 5(3) The real question

Storing or reading information on a user's device needs consent unless it is strictly necessary. The EDPB's 2023 guidelines on the technical scope of that article read it broadly enough to cover software, not only cookies from memory, re-read before review. usage.json and reading the OS are device access for analytics. In our favour: there's no identifier, it's first-party, aggregate only, and limited in time, the profile some regulators have exempted for audience measurement (CNIL's analytics exemption, for example) conditions not re-checked. Germany's TTDSG §25 has no such exemption.

What we build so the stance can change without a new design

  • The client supports a consent mode. In it the notice becomes a question (“Count this install anonymously? [y/N]”, or the app switch shown off). Nothing is counted, and nothing except the question's answer is written to usage.json, without a yes.
  • Consent comes before any count is sent, so the mode is never learned from the analytics reply. It has two sources, and the stricter one wins:
    • The release's own default, built into the client: opt-out, consent-europe (machines whose system timezone is Europe/*), consent-all, or off. Counsel's answer is settled before the release is cut, so a fresh install of that release already behaves correctly with no network at all.
    • A static policy file beside latest.json on pawdelta.com. It's a plain GET with no body, query, cookie or id, the same kind of request as the app's update check. It can only tighten the built-in default (to a consent mode, or off), never loosen it. The client reads it before its first count and again once its cached copy is older than 7 days.
  • When the policy can't be read: no cached copy, or a copy older than 7 days that can't be refreshed, means nothing is sent that run. It fails closed. A policy read happens only after the notice has been shown, and never in CI, air-gap mode or a dev checkout. Air-gap mode and the off switches stop the policy read too.
  • The timezone is read and compared on the device and never sent. It's a rough proxy, which is why consent-europe is an option and not the default.
  • The {"stop": true} reply stays as a kill switch for clients that are already counting. It is never the way consent is learned.
  • Recommendation: launch with the built-in default opt-out, and ask counsel one question before the release is cut: “Is a no-id, aggregate-only, notice-first weekly ping acceptable under 5(3) for EU users, or do we need consent?” If they say consent, the release ships with consent-europe or consent-all built in. The policy file is for tightening later, not for this decision.
11 · Alternatives, challenged

Four other ways to get these numbers, and why each falls short

A · Piggyback on the update check only Do the server half now

Count the app's latest.json fetches as unique per day and week, with the existing site-uniques sketch (IP + user agent). That needs no client change. For the CLI, move the PyPI check behind a pawdelta.com proxy and count that too.

ChallengeThe app fetches on every launch and every recheck, so hits aren't installs, and a sketch over IP + user agent merges a whole office into one. It can't tell a first run from a returning one, so there's no retention. Version and OS would come from user-agent strings the Tauri updater controls whether it sends the app version is unchecked. Moving the CLI check onto our server makes PawDelta a dependency of upgrades, and we'd still break the “no requests to PawDelta” sentence. Adding any id to the update URL would make the update feed into telemetry, so turning off counting would mean turning off security updates. Worth it as a one-day, server-only stopgap (unique update-checkers per day, already covered by the privacy page's sketch wording), but it isn't the answer.

B · Opt-in only Too few to read

Ask at first run, default no, and send only after a yes.

ChallengeThis is the cleanest legally, but it can't answer the question. We have a handful of real users. Opt-in yields a small and biased slice of them: the most engaged, the people who would sign in anyway. The point is to see the people who don't engage, and opt-in hides exactly them. Kept as the consent mode in §10, so it is one switch away if counsel requires it.

C · Random install id, hashed or rotated server-side More than we need

The brief's proposal: a uuid on the client, and HMAC(secret, id) stored on the server with first and last seen weeks.

ChallengeA stable hash per install is pseudonymous personal data. It brings deletion requests (“which row is mine?” needs the id shown to the user), breach exposure, and a weaker ePrivacy case. What it buys over the cohort design is per-install paths (who upgrades when, who churns after which version) and exact removal of copied homes. We don't need either to answer “how many real people, and do they stay”. Rotating the id weekly loses retention, which puts us back at site-uniques. If per-install analysis becomes necessary later, adding an id is easy to do. Taking one away is not.

D · Third-party analytics or a package gateway Wrong trust story

PostHog or Plausible for app and CLI events, or a download gateway such as Scarf in front of PyPI.

ChallengeThe site's privacy story is “no third-party scripts, fonts or pixels” (reCAPTCHA is the one disclosed exception). A gateway that resolves IPs to companies is the opposite of what we'd promise. It adds a processor to the list and a transfer to disclose, and it still doesn't count people who installed the app or used the install script. Our own counter is about 200 lines of server code we already have the pattern for.

Not an alternative: pushing everyone to sign in. Onboarding work in 0.6.2 and 0.6.3 is already doing that, and it is how the 4 sign-ups that never connected anything are visible today. Counting installs is how we'll know whether it works.

12 · What's hard to undo

Six things that are cheap to get right now and expensive later

  1. Breaking “no telemetry”. The README, privacy page and security page say it today. Once a release counts, “brindle has telemetry” is permanent, even if a later release removes it. Rewrite all three in the same change, with a dated “What changed” entry, and put it first in the release notes and changelog.
  2. Shipped clients send forever. Old versions keep pinging for years. The server must accept every schema version ("v") it ever saw and ignore unknown fields. Start with the smallest payload: adding a field later is a privacy-page change, removing one is free.
  3. The endpoint and policy URLs are baked in. Use fixed paths on pawdelta.com, not an API Gateway hostname, so the backend can move. The policy file can switch every client to consent or off before their next count. The {"stop": true} reply stops clients that are already counting.
  4. Defaults only change gracefully in one direction. Moving from opt-out to opt-in later reads as a fix. Moving from opt-in to opt-out reads as a betrayal. The policy file can therefore only tighten: loosening needs a new release, a new notice and a privacy-page change.
  5. “First run” and “cohort” mean what the first release says. If the definition changes, the triangle breaks at that week. Write the definitions into the console's footnote on day one.
  6. Collected data can't be uncollected. Because only counters are stored, deleting a week (or all of it) is complete. That is one more reason not to store an id: with no per-person rows, a deletion leaves nothing behind.

What the owner needs to choose

  1. Default: opt-out with notice, opt-in, or opt-in only for Europe/* timezones? Opt-out sees the people we can't see today. Opt-in mostly doesn't. Europe/* is the fallback if counsel requires consent. Recommend: opt-out, consent mode built and off
  2. Install id or cohort label? The brief proposed a hashed id. This plan counts with no id at all. The price: lost requests are undercounts, and a home cloned onto a same-named machine overcounts. Recommend: no id; add one later only if per-install paths are needed
  3. Lost requests: accept the undercount, or keep idempotency state on the server? Removing duplicates on the server would need a per-request token kept for a week. That is a short-lived id, and it weakens the “nothing identifies a machine” claim. Recommend: accept the undercount; it is small and stable from week to week
  4. First ping on the next run, or the same run as the notice? The next run gives a real chance to say no, but loses people who run brindle exactly once. Recommend: next run (CLI); leaving the first-run screen (app)
  5. The command's name. brindle telemetry off is what people search for, but the word carries baggage. brindle usage-counts off is gentler and less findable. Recommend: telemetry for the command and the setting, “anonymous usage counts” in the wording
  6. Staff machines: send marked internal, or send nothing? Recommend: send marked, show separately
  7. Counter retention: 24 months, or the site's 90 days? 90 days can't show retention past one quarter. Recommend: 24 months for counters, 90 days for the sketch and logs
  8. Ship the update-feed stopgap (step 0) now? Recommend: yes, it's server-only and already disclosed
  9. Release: the first release after 0.6.3, with the privacy pages published the same day. Recommend: 0.6.4 at the earliest, server steps 0 to 2 before it
