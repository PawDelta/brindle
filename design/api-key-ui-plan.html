A chat view for people who run brindle on API keys

01 · Goal and who it's for

Who is this for, and is that the right line to draw?

The goal as asked

Some people use brindle only with API keys: ANTHROPIC_API_KEY for Claude Code, CODEX_API_KEY or OPENAI_API_KEY for Codex, or a native profile on Anthropic, OpenRouter and the like. Today every session they open is a tmux pane running a terminal UI. They should get a native conversation instead: messages, each tool call with its input and output, edits as diffs, permission asks as cards, and what each turn cost.

These people pay per token with no plan cap, so cost per turn and a budget stop matter more to them than to subscribers.

The challenge to the goal

A chat view isn't tied to the credential. A subscriber gets just as much from structured diffs and approvals, and both sets of users run the same Claude Code. The credential matters in two places only:

  • brindle's own harness (brindle.native) must never carry a subscription token: profiles.subscription_token_problem refuses one, because Anthropic's terms forbid it. That harness is for API keys only.
  • Cost: subscribers see plan usage through the status line; key users need dollars.

The plan below draws the line by interface (pane or chat), not by credential, and puts API-key users first in line for the parts that need a key.

A second audience comes free: a browser tab can't show a pane at all. ProviderSurface.tsx says so in its NO_SHELL card ("a browser tab can't show this pane"). A structured view would work in brindle's web UI as well. This plan doesn't scope web, but it shouldn't rule it out (see Q9).

03 · Three genuinely different architectures

Where the structure comes from

Every option ends in the same React view. They differ in who runs the agent and where the structured events come from. The note's "parse the screen" idea is left out on purpose: screen-scraping a TUI is the weakest possible source. The real choice under option A is the transcript file Claude Code already writes.

AOverlay: a structured view over the live pane

cheapest · no process change

How it works

The pane keeps running exactly as it does now. The daemon tails the transcript Claude Code writes anyway (brindle already reads it, in usage.py, rewind.py and history.py), masks it with redact.mask_data, and streams events to a Conversation tab. Approval cards answer the same _hold_for_app holds the inbox cards answer today. For Codex the source would be its rollout file.

Challenge

  • It's a viewer, not a chat. The TUI still owns the conversation. A trust dialog, the auto-mode upsell, plan approval, AskUserQuestion or /model appear only in the pane, and the chat stalls with no explanation unless a "terminal needs you" banner (from screen_state) catches every case.
  • The transcript is written per message: no streaming text, and no "this tool is running now" until it ends.
  • The composer pastes into a TUI. That works for workers today, but it's the path paste_blocked exists to protect.
  • The Codex rollout format is internal and undocumented.

BHeadless driver: the real CLI, run through its structured protocol

real structure · protocol risk

How it works

Instead of a TUI, brindle starts the CLI in its machine mode and keeps it running across turns. For Claude that's claude -p --input-format stream-json --output-format stream-json --verbose --permission-prompts host, with the same --settings hooks and --mcp-config as today. For Codex it's codex app-server, with turns, steering, interrupts, approvals and diffs as typed messages. The runner stays in a pane, as run_headless does, so liveness, pause, reap and cull, which all key on panes, keep working.

Challenge

  • Neither raw protocol is a stable contract. Claude's control messages are documented only through the SDK, and Codex's app-server says [experimental] in its own help. On the Claude side that argues for going through the SDK (B′) rather than speaking the wire directly.
  • We take over everything the TUI did: slash commands, plan approval, AskUserQuestion, image paste, the agent view, Claude in Chrome. Each one has to be rebuilt as a card or left out on purpose.
  • Host prompts arrive only when the CLI would ask. If someone wires approvals there instead of into PreToolUse, auto or bypassPermissions skips brindle's rules without a sound.
  • Two adapters, two lifecycles, and a second Codex hook-trust surface (does -c hooks… trust carry over to app-server?) unverified.
  • B′ (the SDK as a dependency) uses its own bundled CLI by default, which would bypass brindle's version-specific checks (onFailure needs 2.1.295; the auto-mode menu text is from 2.1.319). Setting cli_path to brindle's claude_binary() avoids that. The open costs are a new runtime dependency, its release cadence, and SDK features that need a minimum CLI version, so an SDK upgrade can require a CLI upgrade and the reverse. That's a reason to pin and test the pair, not to hand-roll the protocol.

COwn harness: brindle runs the agent loop against the API

full control · weaker agent

How it works

This already exists. brindle _native <agent> runs NativeAgent against the Anthropic Messages API or any OpenAI-compatible endpoint. It knows its own state without hooks, drains the inbox between model calls, applies the shared policy, holds asks for the app, and writes a masked, structured transcript. A chat view on it needs no new protocol at all.

Challenge

  • It isn't the agent people chose. Six core tools, no subagents, no web fetch, no outside MCP servers, a 32k default context and no prompt caching (zero cache_control in native/client.py). On long Anthropic sessions, the missing cache alone could cost more than Claude Code would for the same work.
  • Becoming a competitive harness is open-ended work. It's a different product from "brindle runs your coding agents".
  • brindle owns every safety check itself. With permission_policy off, Read has no credential-store deny today.
  • Key-only by rule: subscription tokens are refused.

05 · Recommendation

One view, one event model, several sources: A first, then B

A → B, C as a bonus

Build the conversation view once, against a small provider-neutral event model (message, tool call, tool result, file change, ask, usage, status). Feed it first from the transcript (A), for every Claude session, next to the terminal. Then, if the spike passes, add the headless driver (B) as an opt-in "chat" interface that makes the view interactive, for API-key users first. The native harness (C) gets an adapter almost for free, because it already emits these events, but it isn't the product.

Why this order: A tests the view on real sessions with no change to how agents run, and it's worth having even if B fails. B is the only option that makes the chat the interface rather than a mirror of one, but it carries the protocol risk, so it goes behind a spike and a setting. C would mean competing on harness quality, which is a different bet.

Rules that make it cheap to undo

No new source of truth

The CLI's own transcript stays the record. Conversation events are derived on the fly and never stored. Removing the feature leaves nothing to migrate.

The checker doesn't move

PreToolUse remains the point that enforces, in every mode. Host prompts and app cards only ever answer an ask the checker already made. A deny stays a deny.

One process writes a session

"Open in terminal" stops the headless process, then runs claude --resume on the same session id in a pane; "Back to chat" reverses it. Never two writers at once.

The approval loop (green) is the one that exists today: only the card moves. The adapters, the mask and the lock gate are new daemon code. The websocket is the existing daemon/events.py socket.

One-way doors

Expensive to undo. Decide these deliberately, because each is hard to walk back.

  • Moving agent processes out of tmux into the daemon. Liveness, pause, reap, cull, pane_owners, the sidebar and recovery all assume a pane. This plan keeps the runner in a pane on purpose.
  • Storing conversation events as a new record. That means a schema, migrations, and a second copy of every secret to mask. Derive them instead.
  • Making chat the default for anyone before parity, and teaching users that slash commands don't exist.
  • The Claude adapter's transport: the Agent SDK, or the raw protocol. Either way the adapter code is built around it, so swapping later costs a rewrite. Prefer the SDK with cli_path set to brindle's claude, and never ship its bundled CLI, which would bypass brindle's version checks. Pin the SDK/CLI pair, and decide only after G8.
  • Growing brindle.native into a general harness. That's a product commitment with no end, not a feature.
  • A public daemon route for events that web or plugins start depending on.

Cheap to undo

  • The Conversation tab (A): delete the component and the adapter.
  • The chat interface (B) behind a per-profile setting: the pane stays the default.
  • Composer commands and cards: plain UI.
08 · Phased plan, spike and effort

Spike first, then ship something useful at every step

Phase 0~1.5 weeks

Spike: prove the headless driver is safe before building on it

Throwaway code in a scratch branch. Pin claude 2.1.319 and codex-cli 0.162.1. Run under a temporary BRINDLE_HOME and a fresh provider home with only an API key, no subscription. Record every event to fixtures; they become the adapters' tests. Billing estimate: a few dollars of API usage.

G1 · HARD

One long-lived claude -p stream-json process takes three or more user turns on stdin without restarting, and brindle's --settings PreToolUse hook fires on every tool call.

A planted cat ~/.aws/credentials is denied by brindle's hook, not by the host, in default, acceptEdits and auto.

G2 · HARD

An ask reaches the host as a control request with the tool name and full input; _hold_for_app answers it from an app card; a deny propagates; with no daemon, it denies.

Also record whether the PermissionRequest hook fires before the host prompt, and whether the two can be told apart or happen twice.

G3 · HARD

Handover: stop the process mid-session, then claude --resume <id> in a pane continues the same transcript file; then back to stream-json. No fork, no duplicated turns, and can_resume is true at each step.

G4 · HARD

Secrets and credentials: a tool that prints a fake key comes out masked over the websocket. claude_credential() names the credential the process actually used. No first-run screen or key question blocks -p.

G5 · SOFT

Coverage: Bash, Edit, Write, the Agent subagent (--forward-subagent-text) and the brindle MCP tools all render from the stream; Edit events carry enough to draw a diff without re-reading the file.

Interrupt mid-tool leaves the session resumable.

G6 · SOFT

Cost: per-turn tokens and dollars from the result events match brindle.usage's reading of the transcript to within 1%. --max-budget-usd stops cleanly.

G7 · SOFT

Codex half-day probe: app-server thread/start + turn/start with CODEX_API_KEY; commandExecution/requestApproval is answered; brindle's Codex PreToolUse hook runs under app-server with its trust intact.

G8 · SOFT

SDK or raw protocol: run G1–G4 a second time through the Python Agent SDK with cli_path set to brindle's claude_binary() (2.1.319), and can_use_tool wired to _hold_for_app. Record which SDK versions work with that CLI, and whether brindle's --settings hooks, --mcp-config and --append-system-prompt pass through unchanged.

Pass: phase 2 builds on the SDK, with the pair pinned and tested in CI. Fail: phase 2 speaks the protocol directly, using the SDK source as its reference.

Go if G1–G4 all pass: build phases 1–3. Partial (G5 or G6 short): build, and list the gaps in the phase 2 plan. No-go (any hard gate fails): ship phase 1 (A) only, file what failed upstream, and revisit at the next CLI release. G7 decides phase 4 on its own; G8 picks the Claude transport.

Phase 1~3 weeks

Overlay: a read-only Conversation tab for every Claude session

  • The event model and a transcript adapter in the daemon: tail, mask, lock gate, over the existing websocket.
  • ConversationView in ProviderSurface, with a Conversation/Terminal tab switch. The pane stays the default.
  • Inline approval cards on the existing holds; a "terminal needs you" banner from screen_state.
  • Cost per turn from usage.py. A native-harness adapter if it costs under a week.

Ships to everyone, subscribers included. Undo: delete the tab.

Phase 2~4 weeks

Chat interface for Claude, opt-in, API-key users first

  • A profile/session setting, interface = "chat". The runner in its pane (an extension of run_headless) runs one long-lived session: through the Agent SDK with cli_path set to brindle's claude if G8 passed, otherwise over stream-json directly.
  • Composer, interrupt, queued messages, host asks into holds, deny on no answer.
  • --max-budget-usd wired to budget.py; the credential shown in the header.
  • Fixture tests per pinned version; unknown events shown raw.
Phase 3~3.5 weeks

Handover and parity

  • "Open in terminal" and "Back to chat" with one writer at a time.
  • Lifecycle: paused, locked, failed and ended mapped onto surfaceCard; launch_health, watch and wake taught the chat mode.
  • Cards for plan approval and AskUserQuestion; the composer-command shortlist (Q4).
Phase 4~3 weeks

Codex through app-server, if G7 passed

A second adapter on the same event model: turn/steer, turn/interrupt, the two approval requests, turn/diff/updated for diffs and thread/tokenUsage/updated for cost. Sandbox parity with _codex_sandbox checked before it's trusted. Opencode and Antigravity are out of scope.

09 · Open questions for the owner

Decisions this plan can't make for you

  1. Audience: API-key users, or people who don't want a terminal?

    Phase 1 serves both. Is it fine to ship it to subscribers too, or should the whole feature stay a key-user feature?

  2. Default or opt-in?

    After phase 3, should new sessions for key-only users open in chat by default, or always in the pane until they choose?

  3. Interactive chats only, or workers too?

    Supervisors and interactive chats gain the most. Running workers through the chat interface doubles the lifecycle paths to test. I'd start with interactive chats only.

  4. Which slash commands have to exist in chat?

    My shortlist: /compact, /model, /clear, /cost. Everything else goes through "Open in terminal".

  5. Can we depend on Codex's experimental app-server?

    The alternative for Codex is phase-1-style overlay only (rollout files), with no native input.

  6. Should a key change lock a session?

    Today an API-key session records no identity, so it never locks. If someone swaps in another org's key, should that session's conversation hide, as it does for a company sign-in?

  7. Budget defaults.

    Should --max-budget-usd be on by default for key users, and at what amount? Hard stop, or ask to continue?

  8. The native harness's future.

    Keep it a local-model and OpenRouter path (adapter only), or invest in prompt caching and more tools so it competes? This plan assumes the first.

  9. Web.

    A structured view works in a browser tab where a pane can't. Is the web UI a target, which would make the daemon route public-facing and so a one-way door?
