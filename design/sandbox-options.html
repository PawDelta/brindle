    Docker: a socket proxy needs to understand the request

    Proposed broker contract: accept build context uploads and a fixed run schema; construct requests itself. Deny privileged mode, host binds, devices, host namespaces, added capabilities, socket mounts and host networking. Use broker-owned volumes, isolated networking, resource limits and task-owned container IDs; forbid access to other containers, arbitrary API routes, upgrades and build entitlements. A dedicated disposable builder avoids sharing a personal daemon.

    An endpoint-only allowlist is insufficient: container creation carries security-sensitive JSON. Docker’s authorization plugin supports request decisions, but non-JSON bodies and upgraded/gRPC flows have documented limits. Source 3 This broker is not built or audited; arbitrary Compose and Testcontainers compatibility is unverified. Stage file copies instead of host mounts.

    Narrow alternative: rootless Docker removes daemon root privileges, but still has its OS user’s file access. Source 4 Provision a separate service account with no personal home access, or a disposable task VM without personal shares. Share only staged task inputs. This deployment is proposed, not verified here.

    tmux: the server must start inside the boundary

    tmux -S <task-dir>/test.sock -f /dev/null selects a separate server. Start it inside the worker sandbox; deny every host-server socket. A different socket name or file mode alone does not isolate same-user processes. Source 5

    Proposed integration: clear inherited TMUX, configure tests with the task socket, and prove host-server connections fail. A server started by an unsandboxed broker would run its shells outside the worker boundary; that is unacceptable here. Host and peer-worker visibility intentionally breaks.

    SSH: a Git host is not a repository permission

    Use a dedicated agent containing only a task key. Load it outside the worker with ssh-add -c -h git@github.com <task-key>. Destination constraints bind authentication to host keys; they need compatible OpenSSH components and trusted known-host entries. Confirmation uses ssh-askpass. Sources 6–7

    Proposed integration: expose only this agent; protect the confirmation UI from worker control. A host constraint does not scope repositories, refs or commands; use a repo-scoped deploy key or a broker for that. Confirmation is per authentication use, not per Git operation. An established session can do more work; prompts can be misleading. GitHub/server compatibility and this Mac’s askpass path are unverified.

    Broker alternative: fixed remote, repository and ref operations in a controlled execution environment. Ignore worker Git configuration, hooks, credential helpers, environment and custom transport commands; never execute worker-provided shell text outside the sandbox. This broker is not implemented.

    Keychain: release one secret, or keep it in the broker

    Proposed broker contract: owner maps a task to an exact service/account item; the broker validates caller, item and task lifetime. Supply only that token through a private task channel. Prefer a short-lived, narrowly scoped credential; delivering a static secret cannot make it expire or erase copies the worker made.

    Better still, perform a fixed authenticated request without handing out the token. Keep logs free of secret values. Deny direct Keychain service access and backing-store reads. Item ACLs are documented, but a per-item filter in these CLI sandboxes is not verified; the Narrow cell is unavailable. Source 8

    05 / What we know, and what we still need to prove

    Documented does not mean integrated.

    Primary sources checked 06 November 2026. Attack paths are threat-model inferences from documented service powers.

    Documented mechanisms

    Real controls, with limits

    Claude exposes filesystem and network sandbox controls and warns about Unix sockets and Mach/XPC services. Its boundary covers shell descendants, not all tools. Source 9

    Antigravity documents terminal isolation, but --sandbox has no effect when unavailable. Neither documentation page proves the four proposed integrations on this installation. Source 10

    Branch evidence · reported

    feat/os-sandbox @ 576dd7c3

    Inspected src/brindle/os_sandbox.py and docs/investigations/os-sandbox.md via Git. Claude allows the brindle daemon socket and open outbound domains; agy gets file denies and a bypass-denial hook. No component brokers are implemented.

    The branch records synthetic file-denial probes on Claude 2.1.319 and agy 1.5.2 on Mac. Those are the other worker’s results, not tests repeated here. It reports an agy availability gap and untested Linux behavior.

    Unverified · release gates

    Prove the doors actually close

    Test raw socket aliases, TCP endpoints, Keychain API/Mach access and alternate clients under both providers; blocked reads alone do not prove service denial. Verify private tmux children remain sandboxed and confirmation cannot be driven by a worker.

    Audit the reachable brindle daemon’s per-operation authority too. Its socket is an additional door. Confirm broker identity, request validation and task isolation before offering Balanced.

    Private plan: not read. The requested Project 1 item “[Feature] 0.6.3: OS sandbox for Claude and Antigravity workers” could not be fetched: this profile denies gh’s config directory. The branch was used as implementation context, not a substitute for the board’s decisions. Owner/supervisor must reconcile that body before adopting this proposal.
