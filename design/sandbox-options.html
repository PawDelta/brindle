Decision brief 06.03 / 06 November 2026

Four doors out
of the sandbox.

Workers need your tools. They don’t need every power those tools have. Decide what can cross the boundary, one capability at a time.

Recommended direction

Keep the work moving.
Contain the authority.

Choose Balanced as the target: container jobs, private test terminals, constrained Git credentials, and named task secrets.

    Docker: a socket proxy needs to understand the request

    Proposed broker contract: accept build context uploads and a fixed run schema; construct requests itself. Deny privileged mode, host binds, devices, host namespaces, added capabilities, socket mounts and host networking. Use broker-owned volumes, isolated networking, resource limits and task-owned container IDs; forbid access to other containers, arbitrary API routes, upgrades and build entitlements. A dedicated disposable builder avoids sharing a personal daemon.

    An endpoint-only allowlist is insufficient: container creation carries security-sensitive JSON. Docker’s authorization plugin supports request decisions, but non-JSON bodies and upgraded/gRPC flows have documented limits. Source 3 This broker is not built or audited; arbitrary Compose and Testcontainers compatibility is unverified. Stage file copies instead of host mounts.

    Narrow alternative: rootless Docker removes daemon root privileges, but still has its OS user’s file access. Source 4 Provision a separate service account with no personal home access, or a disposable task VM without personal shares. Share only staged task inputs. This deployment is proposed, not verified here.

    tmux: the server must start inside the boundary

    tmux -S <task-dir>/test.sock -f /dev/null selects a separate server. Start it inside the worker sandbox; deny every host-server socket. A different socket name or file mode alone does not isolate same-user processes. Source 5

    Claude proposal: clear inherited TMUX, configure tests with the task socket and allow that exact path via {"host_tmux":"/path/to/test.sock"}. The path control is built and confirmed; the private test-server lifecycle is unverified. Bare host_tmux opens brindle’s actual agent server, including supervisor/other worker panes—it is not a safe test-server shortcut.

    agy: no setting can reopen its tmux socket. Use an external broker running fixed tests in a separate isolated environment, or knowingly remove the provider sandbox. Never start an unrestricted host shell through the broker.

    SSH: a Git host is not a socket permission

    Built: Claude’s ssh_agent opens $SSH_AUTH_SOCK, all or nothing. It cannot filter destinations or keys. A brindle filtering-agent proxy would need to be built and reviewed. agy has no socket-reopen setting. Verified Mac runs

    External OpenSSH alternative, not a brindle feature: a separately provisioned task agent can load a key with ssh-add -c -h git@github.com <task-key>. Destination constraints need compatible components and trusted host keys; -c uses ssh-askpass. This setup and confirmation UI are unverified here. A Git host is not a repository/ref permission, and confirmation is per authentication, not per Git operation. Sources 6–7

    Recommended broker: fixed remote, repository and ref operations in a controlled environment. Ignore worker Git configuration, hooks, helpers, environment and custom transports; never execute worker-provided shell text outside isolation. Keep the personal agent inaccessible. The broker and agy-compatible transport are not built.

    Keychain: a broker alone does not close the open door

    Verified today: security find-generic-password -s nope reached Keychain and returned item-not-found in both sandboxes. No secret was extracted by this canary. keychain in os_sandbox_allow is bookkeeping only; absence does not deny access, and agy has no service-denial control. No working Claude Keychain-denial recipe has been established either.

    Prerequisite for the target: place the worker in an externally isolated environment without the host keychain (for example, a separate VM without host credential shares). Only then can an owner mapping of task → exact service/account item constrain access. The broker validates caller and task lifetime; prefer a fixed authenticated request over handing out the token.

    A delivered static secret can be copied; it does not become revocable just because a task ends. Prefer a short-lived scoped credential. Item ACLs still apply today, but are not a CLI per-item filter. Source 8 The isolation and broker integration are proposed and unverified.

    05 / What do other apps do?

    Keep the vault outside. Share a smaller capability.

    There is no single uniform default across these products. The recommendation below is a synthesis of documented patterns, not an industry certification.

    Pattern to borrow

    Separate storage from use.

    A remote workspace gets a scoped token. Git talks to a credential helper. An SSH agent signs without exporting the private key. These patterns avoid giving a tool the whole credential store.

    Boundary to verify

    A helper still grants authority.

    A returned token can be copied. A forwarded agent can authenticate. A trusted app may run untrusted commands. Require scope, caller validation and an inaccessible direct path—not just a friendly permission prompt.

    06 / What we know, and what we still need to prove

    Documented does not mean integrated.

    Primary sources checked 06 November 2026. Attack paths are threat-model inferences from documented service powers.

    Verified canaries · Mac only

    Runtime results outrank assumptions

    Claude 2.1.319 and agy 1.5.2 both denied the agent and host tmux sockets, and both reached Keychain. Claude reopened the explicitly allowed sockets; agy has no equivalent setting. The agent had no identities, so reachability—not authentication—was demonstrated.

    Docker Desktop was down: its socket test is inconclusive. agy exposed a canary environment token and allowed outbound traffic despite the documented domain controls. Provider results ↑

    Built · source inspected

    feat/os-sandbox @ 0d44a770

    Inspected src/brindle/os_sandbox.py, docs/guide.md and docs/investigations/os-sandbox.md via Git. Owner-only os_sandbox_allow accepts ssh_agent, docker, host_tmux, apple_events and record-only keychain. Unknown names refuse launch.

    Claude enforces exact socket allowances and Apple Events. agy has no such settings; doctor reports that limitation. brindle’s hook denies BypassSandbox:true. No filtering-agent, container or task-secret broker is built. Native file tools and the interactive supervisor are outside this shell sandbox.

    Unverified · release gates

    Finish the integration proofs

    Test Docker with a live daemon; private tmux lifecycle; external SSH constraints/confirmation; agy broker transport; and an outer boundary that actually removes host Keychain access. A canary lookup did not demonstrate secret extraction.

    Audit the reachable brindle daemon’s per-operation authority too. Validate socket aliases and alternative routes. Linux behavior was not exercised here; do not assume Mac exact-path enforcement carries over without the required Linux filtering. Source 9
