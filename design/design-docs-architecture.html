How a supervisor's plan becomes a design that a team reads, changes and signs off before anything is built: the doc engine, the build gate, sharing through the Library, org review rules, and the two parts that are not built yet (the review queue poller and Ask your supervisor).

1TL;DR

  • A plan is a design doc kept by the engine. Every change is an immutable revision in SQLite; comments, suggestions and votes anchor to it (plan_docs.py). The supervisor proposes, and only the person approves: an agent's approval is refused (plans.decide, person=True comes only from the daemon route).
  • Sharing puts one copy in the Library. Teammates comment, suggest, vote and sign off against that copy. The author's engine pulls and then pushes every 30 seconds (lifecycle.SHARED_DOCS_EVERY, shared_docs.sync). It never merges text: if both copies changed, neither is overwritten and the gate says conflict.
  • The build gate is derived, and it fails closed. plans._gate recomputes it on every read from the Library's last answer and the local threads. While it is shut, Approve is refused (409 gate_closed) and new assigns are refused. An approval first asks the Library again and is refused if it cannot (503 gate_unverified).
  • Org review rules are the Library's. It evaluates them on every read and write from the files a revision declares, and a client cannot submit or remove a rule's row. The engine counts only rows it can read in full.
  • Encryption is the Library's existing envelope scheme: a KMS-wrapped key per scope, a key per document, AES-256-GCM, and an Enterprise org's own KMS key if it names one. It is server-side encryption, not end to end.
  • Not built: the engine's review queue poller and a teammate's reader for a shared design; routing for Ask your supervisor. The server half of both exists.
  • What to weigh before shipping: the engine has only ever run against a fake of the Library; the gate is enforced by the author's engine, not by the server; a conflict has no action that resolves it; path rules trust the files a design declares. Sections 15 to 17.

2Background and problem

brindle runs coding agents for one person. For a large goal the session's supervisor writes a planning doc, and the session's queued tasks wait until the person approves it (plans.py module docstring; plans.holding). In 0.6.3 that doc was a step-by-step reader for one person on one machine. design/build-plan.html replaces it in four phases: the doc, team review and the gate, Enterprise policies, and the Library.

Three things were missing for a team:

  • Review across machines. A plan lived in one engine's SQLite file. A teammate had nowhere to read it, comment or say yes.
  • A build that waits for the right people. One person's approval started the work. Round 6 asks for required and optional reviewers and a build that holds until every required reviewer has signed the current revision (design/planning-doc-round6.html §2).
  • Rules an author cannot remove. Enterprise admins need "a design that touches these paths needs Security" to hold whoever wrote the design (design/planning-doc-round6.html §3).

Two constraints shape everything below. Agents run on the author's machine, under the author's own model provider, so no server can physically stop a build. And the Library service already stores encrypted documents per user, team and org, so the backend contract opens with "No additional table or infrastructure is required" (docs/shared-designs-api.md): shared designs are a new payload on the existing document, key and version store.

3Goals and non-goals

Goals

  1. One doc the person reads, edits, comments on and decides, with every change kept as a revision.
  2. Teammates on other machines review the same doc: comment, suggest, vote, sign off.
  3. An unmodified engine starts a shared plan's build only when every required reviewer and every covering org rule has signed the revision on screen, as of a review state it fetched from the Library for that approval. Anything unknown counts as not signed. (What can change between that fetch and the commit is in section 9.3.)
  4. Org rules that the design's author and editors cannot remove, weaken or sign for alone.
  5. No new server infrastructure, and the same encryption guarantees as the rest of the Library.
  6. Text is never lost and never merged without a person seeing it.
  7. A lost network answer never creates a second document, a second thread or a second revision.

Non-goals

  • Live co-editing. No shared cursors, no operational transforms. Two people who edit the same revision collide, and one is told to read again.
  • Server-side prevention of a build. The gate is the engine's. The Library records who signed what; it does not know when building starts (docs/shared-designs-api.md, "Review requests").
  • End-to-end encryption. The Library reads designs in memory to render them, evaluate rules and index them.
  • Email or push notification. A teammate learns of a review from a queue their engine reads.
  • Reviewing code. Branch review and the merge gate are a separate pipeline and are untouched.
  • Answering a teammate's question on anyone else's provider or bill. See 6.9.

5Alternatives considered

Read this first. Neither repository records why each choice was made. The reasoning below is reconstructed from the code and the planning rounds. Where it misstates the real reason, the owner should correct it.

5.1 Where the doc lives

Option A · the Library is the only copy not chosen

The engine holds nothing; every read and write is a Library call. One copy means no revision mapping, no conflict state, and one code path for author and teammate.

It lost on three counts. The verdict is one SQLite transaction that changes the plan's state, records the answer, grants the one revision a redirect asks for and queues the supervisor's message (plans.decide docstring: "It all lands or none of it does"); that cannot span a network call. Free and Pro plans, and anyone in air-gap mode, have no shared Library to hold the plan (analysis_docs.require_entitlement), so a local store exists either way. And the supervisor writes and reads the plan as a local process many times a turn.

Option B · an engine working copy, synced with the Library chosen

The engine's tables stay the working copy, and pro/shared_docs.py keeps the Library's head in step. The cost is real: the Library numbers its own revisions, so plan_shares maps them (local_rev, remote_rev); an accepted suggestion must be replayed on the exact text it was made on (_send_revisions); a lost answer must be recognised later (_landed, _link_own); and two-sided change ends in a conflict that nothing resolves yet (section 16).

5.2 Who enforces the gate

Option A · the server not chosen

The Library would refuse to release something a build needs until the review is complete. It cannot work as prevention: the build is local processes started by the author's engine with the author's own provider. A signed "ready" statement from the server would be checked by the same client that could be patched to skip the check. What a server statement would add is evidence, and that is worth having (open question 2).

Option B · the app not chosen

Disabling the button is not a control. The check has to sit under every caller, including an agent's MCP tools.

Option C · the engine, on facts only the server can produce chosen

The contract says so directly: "The build gate remains the engine's responsibility" (docs/shared-designs-api.md). The server derives who has signed and which rules cover the revision; the engine decides. plans.decide asks the Library again before an approval, then re-reads the gate inside the verdict's own SQLite transaction. That second read is of the stored snapshot (plan_shares.review), not of the server: it guards against another local sync committing a new reviewer between the check and the verdict, and nothing more. An approval is therefore made against the last review state fetched; a reviewer or rule added in the Library after that fetch and before the local commit is not seen (section 9.3, risk 14). tasks.build_gate_refusal refuses assign and handoff while the gate is shut. The residual is stated plainly in section 10: this binds an honest engine, not a modified one.

5.3 How people edit together

Option A · CRDT or operational-transform co-editing not chosen

It removes edit collisions. It also removes the thing review depends on: a sign-off must name one immutable revision ("Every new revision requires fresh sign-offs", docs/shared-designs-api.md), and org rules are evaluated from one revision's declared files. The head is one sealed blob rewritten whole on every commit (backend analysis_designs._commit), so a stream of small operations would need a different storage and key design. And the main author is a supervisor that publishes whole revisions, not keystrokes.

Option B · immutable revisions, suggestions, and a compare on the revision on screen chosen

Every write carries rev. If it is not the current one the answer is 409 stale with the current number, on the engine (plan_docs._on_screen) and on the server (analysis_designs._on_screen). People who do not have edit rights propose text as suggestions. The cost is that simultaneous editors collide and one reloads.

Option C · section locks ("Sam is editing") not built

Round 6 draws presence on a section. Nothing in either repository implements it. It would cut collisions without changing the revision model, and it is listed as an open question.

5.4 How a teammate hears they were asked

Option A · org-wide notices not chosen

One feed per org or team that every member's engine reads and filters. One write per event, but every reader pays for every event, the feed names designs that some readers may not open unless each read filters by access, and a person-to-person share has no org to post to.

Option B · a sealed per-person queue that carries the card's text not chosen

Each item would hold the title, author and rule names, sealed under the person's scope key. A read is then one decrypt. But the copy goes stale on every rename and revision, it outlives a revoked share, and it moves an org's text under a personal scope key, outside the org's own KMS key and its revocation.

Option C · a per-person queue of pointers chosen (server built)

An item is the design's id and two times, in the person's own scope: "An item stores only the design's ID and times" (docs/shared-designs-api.md; backend analysis_designs.request_reviews). The title and rule names come from the design at read time, with the caller's own access, and an item that no longer applies is deleted by the read (review_requests, _open_request). The cost: one read opens up to 100 designs (MAX_LISTED), and a GET has side effects.

Option D · push deferred

There is no channel from the Library to an engine; the engine polls. Email would carry titles outside the encryption boundary.

5.5 Where encryption ends

Option A · end to end, keys held by clients not chosen

The server could not evaluate rules from a revision's declared files, could not stamp authors and anchors, and could not render, index or search. Governance needs rows a client cannot forge, so the server has to read the design.

Option B · the Library's envelope encryption, unchanged chosen

Scope keys wrapped by KMS, one key per document wrapped for each scope it is in, and an Enterprise org's own key where it names one (backend analysis_docs.py module docstring). Section 10 says exactly what the server can see.

6Detailed design

Figure 1 is the whole system. The author's machine holds the working copy and makes every decision about the build. The Library holds the shared copy and is the only place that knows who signed and which org rules apply. A teammate's machine holds no part of the plan.

6.1 The doc Built

Revisions. Each revision is one plan_revisions row: the lede, the sections, the decisions, the split, the restated ask, and the ids of the sections it changed (plan_docs.insert_revision). The plans row always holds the current one, so older readers of a plan's markdown keep working. A plan from before revisions were kept has no row; its current revision is read from the plans row and stored the first time it is replaced (plan_docs.revision, keep). Section ids are stable, so a comment follows its section across revisions.

Anchors. A thread anchors to a text range, a diagram, a decision or a whole section (plan_docs._anchor). A text anchor stores the section, the offsets and the quoted text. At write time the quote is found at the given offset or at its nearest occurrence (_locate), because the app counts in UTF-16 and the engine in code points (PlanReader.tsx sendDraft). At read time it is found again in the current revision and reported as current, moved or detached (_where). An insertion point has no text of its own, so it keeps 32 characters either side (CONTEXT) and is detached, never guessed, when that context is gone (_insertion).

Threads. A row of plan_threads is a comment, a suggestion or a reply. A comment is resolved and reopened; a suggestion is accepted or rejected (resolve, accept, reject). Authors are person, supervisor or teammate:<sub>.

Edits. A direct edit and an accepted suggestion both go through plan_docs._apply, which claims the next revision number with UPDATE plans SET rev = r+1 … WHERE rev = r AND state = 'open'. A second edit made against the same revision, from another window, is refused with 409 stale; nothing is merged blind.

What reaches the supervisor. Comments and edits do not interrupt the supervisor. They travel with the person's next verdict: plan_docs.pending collects every open thread and reply not yet sent, labels a teammate's as "from teammate", and mark_sent records them in the verdict's transaction. The supervisor answers a thread with plans.reply (the reply_plan_thread tool).

Safety of content. An SVG section is parsed and checked element by element and attribute by attribute against an allowlist; references may only point inside the drawing (plan_docs._svg, _svg_value_ok). Text that looks like a secret is refused before it is stored (visuals._refuse_secrets, called from comment, suggest, _apply and plans.propose).

6.2 The plan and the build gate Built

Proposing. Only the session's supervisor proposes (plans.propose: 403 for anyone else), and only when the person asked for a planning doc or redirected the last revision; without that grant the call is refused as plan_request_required. A session has one undecided plan at a time (409 open_plan).

Holding. While a plan is open or redirected, tasks the session assigns are queued and stay queued (plans.holding, tasks.plan_holds). For a plan that is not shared, the hold lifts if the app disconnects, "so nothing waits on a verdict nobody can give". A shared plan is held with or without the app (plans.holding docstring).

Deciding. plans.decide accepts only person=True, which only the daemon's route passes (routes_visuals.decide_plan). The verdict is one transaction: the state is claimed from open on the revision on screen, so a second click is refused as decided; the threads it carries are marked sent; a redirect grants one revision; and the message to the supervisor is queued in the same transaction. Pushing the message to the supervisor's terminal happens afterwards and loses nothing if it fails.

How the gate is derived. plans._gate returns nothing for a plan with no plan_shares row: a plan that is not shared has no gate. Otherwise the first rule that matches decides:

Three details carry the weight. Sign-offs count only when they name the Library's head revision and that head is the revision on screen (plans._signed, the current flag). A rule row counts as met only if its own fields back the claim: enough distinct signers for met, a waiver with a name and a reason for waived (review_policies.backed). And one sign-off counts for every rule it meets: a listed reviewer who can meet a rule adds no second row (plans._gate, the meets list).

Where the gate is enforced. In three places, all in the engine: plans.decide syncs with the Library first (_check_with_library; 503 gate_unverified if it cannot) and re-reads the gate from the stored review snapshot inside the verdict's transaction (409 gate_closed); tasks.build_gate_refusal makes assign and handoff answer "Nothing was queued" while it is shut (mcp_server.py); and plans.holding keeps already-queued tasks from starting.

6.3 Sharing and sync Built

Sharing. shared_docs.share needs the analysis_docs_team entitlement (_require_team). It claims the plan first (_claim_new), so two shares at once never make two documents. It creates the document in the author's own user scope, with the plan's id as source.ref, then shares that one document with the team or org scope (_create; POST /analysis-docs/{id}/share). Reviewers are given the right to comment and suggest, added to whatever grants exist because the server's PUT /permissions replaces the list (_grant). The Library's answer to the reviewers call is kept as the plan's review state (_remember).

Identity. The link belongs to the account that shared; another account is told to log in to that one (_own). Everything pulled is stored as teammate:<sub>, whoever wrote it, so a vote from the Library can never become the local person's confirmed pick (shared_docs.py module docstring).

Sync. shared_docs.sync does three things in order: take the Library's head as a new revision if a teammate moved it and nothing changed here (_import); bring back threads, replies, votes and the review state (_pull); send what was done here (_send). It pulls first so that a refused send still leaves the teammates' comments on the author's screen. Section 9 walks the conflict cases. The daemon runs it for every shared plan still in review every 30 seconds (lifecycle._watch, shared_docs.sync_open), and the engine runs it before a sign-off, an override and an approval.

The author as a reviewer. shared_docs.sign_off syncs first and refuses unless the revision on screen is the Library's head, "so what they read is what they sign".

6.4 Org review rules Built

On the server. Each org keeps one list of rules, sealed under its org scope key (backend analysis_review_policies.put_policies). A rule says when it applies (paths, a label, or every design), who must approve (a team, a role or a person) and how many approvals it needs. Rules are matched against only the files a revision declares, its workers' files and its options' touches, normalised so that ./x/../billing/a.py cannot dodge billing/** (_declared_paths, _clean, glob_matches). They are evaluated on every read and write, with team and role membership read live (applied, rows). An author's own sign-off does not meet a team or role rule (_counted). A waiver clears one rule for one revision; a stand-in's sign-off counts until a set time (analysis_designs.override_policy).

In the engine. pro/review_policies.py stands between the server's rows and the gate. readable and pending_agrees decide whether a row can be believed; a row that cannot shuts the gate and never drops out of it. ask wraps every Library call about a plan's review and, when the answer is 403 policy_denied or 503 key_unavailable, records it on the plan (refused). The gate then stays shut until the Library next gives a whole answer, and an answer older than the refusal cannot clear it (shared_docs._Head.refused). An admin's waiver, stand-in or Ask again syncs first, so it applies to what the admin read, under the Library's own number for it (_admin_post).

In the app. The doc shows each covering rule as a row nobody on the doc can remove, with who met it and who opened the design (DocPolicies.tsx). The admin page saves the whole list at the version it read, shows what a draft would do to designs in review before saving, and leaves the question of who may save to the Library (Settings/ReviewPolicies.tsx; routes_visuals.review_policies_save, review_policies_impact).

6.5 Folders Built

A design has exactly one folder reference. A new design goes to its scope's default Designs folder unless one is named (backend analysis_folders.default_folder). Folder names and settings are sealed under the scope key. Placing a design in a shared folder gives that folder's audience read access; moving never changes reviewers or sign-offs and never withdraws an existing share (analysis_designs.move; docs/shared-designs-api.md, "Folders"). The engine's client caches nothing (pro/library_folders.py).

6.6 The daemon and the app Built

Every daemon route sits behind Guard: a 32-byte token made at each start and written only to a file the user can read, no foreign browser origin, and on the Unix socket a refusal of any caller that is one of a brindle agent's processes (daemon/auth.py). The plan routes each answer with the whole plan as it is now, gate included (routes_visuals._plan_now). A Library failure is passed through with its own status, so a stale version stays a 409 and an unreachable Library is not mistaken for being signed out (routes_visuals._library).

The doc screen sends one write at a time and replaces its state with the engine's answer (PlanReader.tsx send). On a 409 that is not the gate's, it tells the person the design changed and reads it again. A draft whose text changed under it is not sent at all.

6.7 The Library service Built not merged

A shared design is an ordinary Library document with a design payload inside its sealed head: the current content, threads, permissions, reviewers, votes, sign-offs, revision metadata, the folder, labels and policy overrides (backend analysis_designs.initialize). Every write follows one path, _commit: check entitlement and switches, seal the head, refuse it over 350 KiB, then one DynamoDB transaction that replaces the head only if its version is unchanged, archives the retiring revision, and writes or deletes share rows (dynamo_store.commit_analysis_design). Then it writes an audit row and queues review requests. A read returns view: the stored state plus what is derived each time, such as anchor positions, votes for the head revision, pending reviewers, the rule rows and ready.

The server stamps every author, voter, signer and time from the authenticated caller; a client cannot supply them (design_models.py module docstring).

6.8 The review queue Server built Poller planned

What exists. When a design is created in a shared scope, shared, moved, revised, or has its reviewers or labels changed, the server writes one item per person it now asks, in that person's own scope: the design's id and a time (analysis_designs.request_reviews, at most 500 people per change). GET /me/analysis-docs/review-requests reads the caller's newest 100 items, opens each design with the caller's own access, returns the ones still waiting on them, and deletes the rest (review_requests, _open_request). An item stops applying once the person signed the current revision, has an open comment or suggestion on it, lost access, or the review is over.

What is planned. Nothing in the engine or app reads that endpoint. The plan, with every name and number a proposal:

  • A poller beside lifecycle._sync_shared_docs, on its own task, for any signed-in account with the analysis_docs entitlement.
  • A local table of what was last seen (design id, revision, since, asked_at), so a card is raised once per ask and retired when the item leaves the server's answer.
  • A new Inbox kind, "Design to review", that opens the teammate's reader (F15). design/planning-doc-round6.html §2 draws the card.
  • Proposal poll every 60 seconds. Each poll makes the server open up to 100 designs, so the cadence should be agreed with the backend's cost (open question 4).

6.9 Ask your supervisor Server built Routing planned

What exists. The server accepts a root comment with question: true and a reply with from_supervisor: true. The reply's parent must be a question and the replier must be the person who asked, "so nobody else can answer as someone's supervisor" (docs/shared-designs-api.md; backend analysis_designs.comment). In the app, the highlight bar already offers "Ask the supervisor" (PlanReader.tsx, DocReview.tsx), but the draft is sent as an ordinary comment, which reaches the supervisor only with the person's next verdict. The engine neither sends nor reads either flag.

The rule, as the owner set it. A question is answered by the asker's own supervisor, on the asker's own provider and bill, or not at all:

What the engine needs Planned

  • A way to mark a thread as a question locally, sent as question: true, and delivery of the question to the answering supervisor at once rather than with the next verdict (today only plan_docs.pending carries threads to a supervisor).
  • Sending the supervisor's reply to the Library as the asker's, with from_supervisor: true. Today a supervisor's reply never leaves the machine: shared_docs._unsent sends only rows written by the person.
  • Reading question on pull and leaving questions out of the gate. Today shared_docs._pull_thread ignores the flag, so a teammate's open question would be read as a comment and counted as a request for changes (plans._gate, asked). This must land before teammates can ask (risk 9).
  • For the third path, a supervisor that can read the doc and nothing else. What it may read beyond the doc is an open question (6 in section 17).

The from_supervisor flag is the asker's own statement. The server checks who posts it, not that an agent wrote it (section 10).

8Data model

Three counters, three meanings. visuals.rev counts the supervisor's publications. plans.rev counts every revision, the person's edits and teammates' imports included, so it runs ahead (plans.propose, the comment in write). The Library's content revision (doc_version, payload["version"]) starts at 1 for a new document and counts only what reached the head. Separately, the head item's version attribute rises on every commit, review-state changes included, and is what the transaction compares (dynamo_store.commit_analysis_design).

What is not stored. The gate has no column. The Library's ready, pending_reviewers, policy_reviewers and anchor states are computed on each read (analysis_designs.view); the engine caches the last answer in plan_shares.review and derives the gate from it.

9.2 Revision mapping

The Library numbers its own revisions, so plan_shares holds a pair: remote_rev, the head's number when the two last matched, and local_rev, the local revision that head holds. The head is "current" for the gate only when local_rev = plans.rev and the stored review names remote_rev (plans._gate). One local revision does not always become one Library revision. A suggestion accepted here is replayed as the Library's own accept, which makes the revision and closes the thread together; if the head does not hold the text the suggestion was made on, the revision before it is sent first (shared_docs._send_revisions). A step that fails stops the rest, and the text waits.

What an approval is consistent with. Two different windows exist, and only one is closed. plans.decide syncs with the Library (_check_with_library) and then opens its transaction, in which _gate reads plan_shares.review. If a background sync commits a new reviewer between those two steps, the transaction sees it and the approval is refused: that window is closed. But the transaction does not ask the server again. A required reviewer, a rule change or a new head that reaches the Library after the sync's response and before the local commit is not observed, even by an unmodified engine, and nothing notices afterwards, because the background pass stops syncing a plan once it is approved (shared_docs.sync_open). An approval is a decision on the last fetched review snapshot. The server has no conditional "approve if the review is still at this version" call that would close the second window (risk 14, open question 2).

10Threat model

Encryption here is at rest, not end to end. PawDelta's service decrypts a design in memory every time it serves or changes it, and sends each new revision's text to the Library's reader (analysis_designs._revise calls analysis_reader.read_document; the reader is a small Claude model with a text-only fallback, config.ANALYSIS_READER_MODEL). A customer who must keep design text from PawDelta's running service should not share designs.

10.1 Assets

  • The design's text and discussion. Architecture, file paths, sometimes security reasoning.
  • The integrity of the review. Who signed which revision, which rules applied, who waived what and why.
  • The authority to start a build. Agents then run on the author's machine with the author's credentials.
  • Credentials. The Library sign-in, the daemon's token, the provider keys.
  • Org structure. Members, teams and roles, as far as rule rows reveal them.

10.3 Keys

10.4 What the server can see

  • While serving a request: everything in the design. It needs the text to render the canonical file, place anchors, match rules against declared files, index and run the reader.
  • At rest, without KMS: the fields in Figure 5's "in the clear" box. That includes who owns a document, which scopes it is shared into, who shared it and when, who is waiting in whose review queue, and who opened a design. It does not include any text.
  • In the audit table: event names, the actor, the IP, the document id, the revision, and for rule events the rule id, a stand-in and its end time. "The reason is not written to the audit log" (docs/shared-designs-api.md; analysis_designs.override_policy).
  • With BYOK, for docs an org or its teams own: the org can cut the service off by disabling its key. Those docs become unreadable through every scope on the next request (analysis_docs._owner_gate). A disabled key can be re-enabled; a deleted one cannot, so those Library copies are then lost for good. Copies on people's own machines are untouched either way.
  • With BYOK, for a design shared from the engine: less than that, as I read the code. The engine creates the design in the author's personal scope and then shares it (shared_docs._create), so the personal scope owns it. A personal scope always uses the service key (scope_key_bytes: BYOK only for group and org), and _owner_gate applies only to docs with an owning org. So after the org disables or deletes its key: teammates can no longer read, because their team or org scope key will not unwrap; if the org has review rules, every read of the review view answers 503 key_unavailable, because the rules cannot be opened (analysis_review_policies._load), and the engine's gate shuts. But the document key is still wrapped under the author's personal scope and the service key (analysis_editing._open, analysis_docs._doc_key), so the ciphertext stays openable by the service, and for an org with no rules the author's reads keep working. The cut-off BYOK promises is therefore not complete for these designs. No test covers this, and it should be confirmed before BYOK is described to a customer as covering shared designs (risk 13).

What follows from the constants

  • Background reads. One shared plan in review costs one GET …/design every 30 seconds: 2,880 a day (86,400 ÷ 30). Each one writes an audit row (analysis_designs.get) and unwraps at least one scope key through KMS, because scope keys are never cached. The cost grows with open reviews, not with activity.
  • Either the head's size or its thread count can bind first. The head is compressed before the 350 KiB check (analysis_docs.seal, then analysis_designs._commit), so which limit a review reaches depends on its content. 500 comments at the server's 8,000 characters is 4,000,000 characters before compression, which will not fit unless it compresses more than tenfold; 500 short comments reach the count limit with room to spare.
  • The engine and the Library disagree on two bounds. A comment may be 8,000 characters in the Library and 2,000 in the engine; a design may be 512 KiB there and 256 KiB here. A teammate's longer comment is stored as pulled; a teammate's larger revision is refused on import (shared_docs._readable: "too big to read here").
  • The planned poller. One poll makes the server open up to 100 designs, each with its key unwraps and rule evaluation.

Proposal Before launch, agree a target for how many shared plans one org keeps in review at once, and measure the read cost at that number. No such figure exists today.

13.2 Gaps

  • No record of the build. The author's approval and the tasks it released are known only to the author's engine. An auditor cannot tell from the Library whether a build waited for its sign-offs.
  • The author's background sync is audited as a read every 30 seconds, which buries the reads that matter. The "opened by" list already leaves the author out for this reason (analysis_review_policies.note_open).

14.3 Migration

  • Engine. The new tables are created if absent (db.py schema). A plan from before revisions were kept needs no backfill: it is read from its plans row and stored on first change (plan_docs.revision, keep). Threads written before a plan is shared are linked to no Library thread and are never sent (shared_docs._linked).
  • Server. No new table. A design is a flag and a payload on the existing document item. Threads saved before questions existed read as question: false (analysis_designs.view).   • Key rotation. Changing an org's BYOK key re-wraps its document keys and re-seals its folders and rules (analysis_docs._rekey_org).

14.4 Order Proposal

  1. Merge and deploy the backend first. It is additive, and an engine that never calls it is unaffected.
  2. Run the engine's shared-doc tests against that deployment before merging the engine (section 15). This is the step that has never happened.
  3. Merge the engine and app with sharing reachable only for staff until two real machines have completed Figure 2 end to end.
  4. Ship the poller and the teammate's reader together; neither is useful alone. Ask your supervisor follows, after the gate ignores questions.

15.2 What is unverified

The engine has never talked to the real backend. Every engine test of sharing runs against a fake written from the API document. The two halves were built on separate branches and neither is merged. Any place where the fake and the server differ is untested.

  • The contract itself. Field names, status codes and error bodies as the server really returns them. The fake always answers policy_reviewers: [] in the sharing tests, for example (tests/test_shared_plan_docs.py, Library.view).
  • Two real machines. No teammate client exists, so no run has had a second person sign off. A teammate's side in the tests is the fake's state being edited by hand.
  • Content equality across the wire. _landed and _import compare the head's content with a local revision field by field after masking. If the server normalises anything on the way in (whitespace, defaults, key order inside lists), a lost answer would be read as a conflict.
  • DynamoDB under contention, real KMS, and BYOK revocation and deletion. In particular, section 10.4's reading that a design owned by the author's personal scope stays readable after the org revokes its key.
  • The entitlement lapse path in section 11, which is intent, not code.
  • Size and time. No test approaches the 350 KiB head, 500 threads or 1,000 revisions, and nothing measures how long a sync or an approval takes.
  • Offsets. The app converts UTF-16 offsets to code points for the engine. Whether the server counts the same way for text outside the basic plane is untested; both sides fall back to finding the quote, which should hide a mismatch.
  • This document's reading of the backend. I read the modules named in the appendix at one commit. I did not read analysis_editing.py beyond the functions the design module calls, nor the routes file.

1The two halves do not fit.The engine was tested against a fake; nothing has run end to end; neither branch is merged.Section 15.3, items 1 and 2, before either merge.
2The gate binds only an honest engine.It is enforced on the author's machine, and the Library is never told a build started.Report the build's start to the Library, so a skipped gate at least leaves evidence. Say plainly in the product that this is a team process control, not a security boundary.
3Path rules trust the design.Rules match only split[].files and options' touches; "Prose is never matched". 4A conflict is a dead end.No route or screen resolves it. The only way out in code is the Library's head coming to equal a local revision (_landed).An action on the gate: take the Library's text as the next revision, or send mine on top of theirs, each as an explicit new revision that needs fresh sign-offs.
5A lapse or sign-out strands a shared plan.Approval needs a successful sync, and a sync needs the Team entitlement and the sharing account. The intended downgrade to a personal doc is not written.Write the verified-lapse path; keep every unverifiable case closed.
6The background pass is costly and noisy.2,880 audited reads and at least as many KMS calls per plan in review per day.A cheap "has the head changed" check (the item's version) before the full read; mark background reads in the audit.
7A teammate can steer the author's supervisor.Request changes forwards teammates' open threads into the supervisor's context, and the supervisor acts with the author's permissions.Show the author exactly what will be sent; fence teammates' text as quoted material in the message.
8A long review can fill the head.All threads live in one sealed item of at most 350 KiB after compression, capped at 500 threads and replies, and resolved threads are never moved out. Which bound is reached first depends on the content.Archive resolved threads with the revision they closed on.
9A question shuts the gate.The engine ignores question on pull, so a teammate's question counts as a request for changes.Read the flag and leave questions out of asked, before any client can ask.

13BYOK does not fully cover a shared design.The engine creates a design in the author's personal scope, which uses the service key, so the document key stays wrapped outside the org's key (section 10.4). Read from the code; not tested.Create shared designs directly in the team or org scope, which the API allows, or stop wrapping the key for the personal scope once an org scope holds it.
14An approval can miss a reviewer added a moment before.The verdict's transaction reads the stored review snapshot, not the server. 17Open questions

  1. How is a conflict resolved? Take theirs, keep mine on top, or always ask? Each choice is a new revision and resets sign-offs.
  2. Should the Library learn that a build started? It would close the review on the server, clear queue items, and give auditors evidence. Made conditional on the review's version, it would also close the window between an approval's last fetch and its commit (risk 14). It also means the server holds a fact about the author's machine.
  3. Where does a teammate read a shared design: the app, or a page on the website? And does their machine keep a copy after they lose access?
  4. How often may an engine poll the review queue, given what one poll costs the server? Is a change marker needed first?
  5. Should declared files be checked against what was built? If so, at merge time, and what happens to a build already running?
  6. Ask your supervisor: what may the read-only supervisor read besides the doc? Is its cost shown before it runs? Is "no usable provider" decided per provider or per account? Are answers kept when the question is resolved?
  7. Are a supervisor's ordinary replies mirrored to the Library, and if so under whose name?
  8. What happens when a review outgrows the head? Archive, split, or refuse?
  9. After a verified lapse, what becomes of teammates' comments and sign-offs on the doc that is now personal?
  10. Section presence ("Sam is editing"). Round 6 draws it. Is it wanted, given that it needs a live channel the Library does not have?
  11. Which scope should own a shared design? Today the author's personal scope does, which keeps it outside an org's BYOK key.
  12. Who reviews this design? The header proposes three roles and names nobody.
