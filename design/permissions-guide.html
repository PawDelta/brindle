How brindle decides what your agents may do

Every time an agent wants to read, write, run a command, push or use a tool, brindle checks it against a short ladder. Most requests are settled without you. The rest arrive in your Inbox as one grouped question.

The decision ladder

A request is checked against every rule. Deny beats ask, and ask beats allow.

From your preset or added by you. This includes read-only commands (grep, cat, ls, git log), which run only when brindle can fully parse them; the rule is removable and Secure doesn't have it.

Your "unmatched actions" setting: ask, allow and log it, or deny.

What changes

Before and after this PR

Today (0.4.7)

  • ✕Built-in denies you can't remove, like the git push deny that stalled workers
  • ✕Read-only commands brindle can't parse stop and ask
  • ✕One question per file, per branch, per command
  • ✕Two overlapping systems: Lenient/Balanced/Strict editor plus daemon grants
  • ✕permission_essentials adds asks even with the policy off

After PR #281

  • ✓No built-in rules. Every rule, defaults included, is editable and removable
  • ✓Read-only commands that brindle can fully parse run
  • ✓Grouped, generalized requests: one answer covers them all
  • ✓One system: presets, rules, saved actions. Your old settings convert automatically
  • ✓Org approval limits for Team organizations stay as they are
One switch left in config
configpermission_policy turns all of this on or off for a repo. Without an explicit setting it defaults on only with the learned-rules license capability, and off otherwise. Turning it off stops brindle's rules; strict agy still enforces policy and other profile and hook protections remain.
