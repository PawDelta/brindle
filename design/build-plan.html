The doc

PR 1 · replaces today's step-by-step reader

One scrolling design doc for a single person: what you review, decide, comment on and edit before anything is built.

Doc engineheavy · engine
  • Plans as revisions: sections, diagrams, decisions with options, pros/cons, files and votes
  • Comments anchored to a text range, a diagram or a decision; replies, resolve
  • Suggestions (before/after) and direct edits, each a new revision
  • Attachments on comments and notes
The doc screenFable · app
  • Doc layout, review column with "To decide" checklist, bottom bar in two rows
  • Viewing / Suggesting / Editing; highlight to comment
  • Next decision led by the bottom bar, green divider
  • Request changes and Confirm / Sign off
after Doc engine
Supervisor writes design docsmedium · engine
  • propose_plan takes sections, mermaid/SVG diagrams, decisions and the split
  • Comments and suggestions reach the supervisor; it answers threads and publishes the next revision
after Doc engine
2

Team review and the gate

PR 2 · Team plan and up

Sharing a doc with teammates, required and optional reviewers, sign-offs, and a build that waits for them.

Shared docs on the serverheavy · pawdelta-web + engine
  • A shared doc's revisions, comments, votes and sign-offs live in the Library service, so teammates on other machines see the same doc
  • Permissions: can edit / suggest / comment
Reviewers and the gateheavy · engine + app
  • Required / optional reviewers; edit the list after sharing (editors)
  • Build holds until every required reviewer signs off the current revision; decision or split changes reset sign-offs
  • Once building, review closes; a new revision reopens it
after Shared docs
Inbox for teammatesmedium · app + engine
  • Review requested, changes requested, reviewers changed
  • Opens the doc at the right place
after Reviewers

Enterprise policies

PR 3 · Enterprise plan
Review policiesheavy · pawdelta-web + engine
  • Admin settings: paths, labels or any design → a team, role or person
  • Locked reviewer rows; one sign-off counts for every rule it meets
  • Re-checked on every revision; audit log
Overrides and rolesmedium · app + server
  • Waive once with a reason, or name a stand-in (admin roles)
  • Who may change reviewers or create org folders
  • "Blocked by org policy" view
after Review policies

The Library

PR 4 · can ship before 2 and 3
Knowledge becomes the LibraryFable · app
  • Stacked-documents button in the sidebar foot beside the terminal switch, with the needs-you dot
  • The app sidebar becomes the Library's (← Sessions); Settings loses its Library heading
  • Recent, Pinned, Stage, Folders, Sources
Search, filters and the recordmedium · app + engine
  • Search on top across docs, comments and decisions; Type, Stage, Shared, Author, Reviewer, toggles
  • A design's record: revisions, sign-offs, decisions, PRs; empty state
Foldersmedium · pawdelta-web + engine
  • Personal, team and org folders, private or shared
  • Who can add; moving never changes reviewers
What's hard or worth knowing
Phases 2, 3 and folders need the server. Team review across machines means shared docs, comments and sign-offs live in the Library service (pawdelta-web). That's a backend change and a deploy, not just the app.
Phase 1 replaces the step-by-step reader that shipped in 0.6.3. Until PR 1 lands, plans keep opening in the current reader.
Size. About 13 workers. I'd expect phase 1 in a day of worker time, phases 2 and 4 next, phase 3 last.
How it's checkedEach task has a test that fails first; each phase has a milestone check; I screenshot the real screens and show them to you here before each PR.
