01 / Decision order

Follow one request through the engine

The provider turns structured tool input into a Request: provider, kind, tool, cwd, worktree, repository, and command / path / URL. The shared engine does not infer authorization from terminal text. These steps describe permissions.decide; the provider-specific boundaries follow in section 08.

  1. Can the request be read?

    A missing request or unknown kind returns Ask. Load the current store, repository denies, organization denies, and the caller’s profile rules.

  2. Does any active rule deny it?

    Check the whole request, then restrictions inside shell commands. A deny on a part beats an allow of the whole. Expired rules, other-repository rules and excluded requests do not match.

    Yes → DenyOtherwise ↓
  3. Does a live saved deny cover it?

    Check scope, kind, repository, expiry and session. This happens before automatic allows.

    Yes → Deny
  4. Which rule wins: ask or allow?

    An explicit ask beats every matching allow, regardless of specificity or order. With no whole-command result, a supported compound runs if every part is allowed by a rule. A part’s deny still wins.

    Ask → Keep its limits ↓Allow → Return Allow
  5. No covering rule? Apply “Unmatched actions”

    deny or allow returns that decision immediately. ask proceeds to saved allows. Shell restrictions can already have produced a bound ask, preventing this fallback.

  6. Can a saved allow settle this ask?

    It must cover the request and satisfy every matching ask rule’s limits, current organization limits, expiry, session and any migrated bindings or remaining-use budget.

    Yes → AllowNo → Ask the person

Precedence is deny → ask → allow → unmatched. A more specific allow does not punch through a broad deny or ask. Multiple asks accumulate limits; the engine displays the strictest applicable ask. Saved denies also stop requests that rules would allow.

02 / Rule anatomy

A rule is data you can inspect

The local store is ~/.brindle/permissions.json (under the configured brindle home). Preset, user and accepted learned rules live together. Repository .brindle/permissions.json contributes deny rules only. Profile permission_denies and organization denies can narrow the policy too.

kind: bash             match_type: push
match: * → @default    decision: ask
limits: { max_scope: destination, life: time, minutes: 30 }
kindWhich action?

read · write · edit · bash · fetch · mcp · other. A push rule is kind bash with match type push; saved actions have a separate push kind.

match_typeHow to compare?

exact, prefix, or glob. Globs use case-sensitive fnmatch: * crosses slashes; ** has no special recursive meaning. No regular expressions.

match / targetWhat to compare?

Bash: full command. Files: resolved absolute and root-relative forms; restrictions also inspect the spelling given. Fetch: URL. MCP / other: tool identifier. ~ expands in file patterns.

decisionAllow, deny, ask

Any deny wins. Otherwise any ask wins. Allows are considered after those restrictions. Exclusions subtract requests from that rule, rather than directly approving them.

rolesNo local role selector

Rule has no roles field, and this branch’s local editor has none. Profile denies are separate. Organization role assignment is a separate policy service, not a role field on local rules.

repo_rootWhere it applies

An optional resolved absolute repository root confines a rule to that repository. Absent means every repository. Editing a stored rule preserves its repository restriction.

expiresRule lifetime

Optional epoch expiry, after which the automatic rule does not match. The editor offers a duration or until deleted. This is separate from how long a member may save an approval.

limitsSaved approval ceiling

On ask rules: max_scope, life and optional minutes. Push scopes use ordered levels; other kinds use a pattern-prefix boundary. life: once allows no saved approval.

id / source / exclusionsIdentity & provenance

Source records preset, user, learned, repo, profile or org. A label names a rule. Editing a preset rule makes it user-owned. Exclusions must have the same kind as their parent.

Named matchers are code, not glob patterns

tracked checks whether git tracks a file; check matches a configured repository check; git-readonly validates status/diff/log/show; git-push recognizes pushes; git-force catches force flags and forced/deleting pushes; push compares source → destination (optionally @ remote); worktree checks resolved paths inside worktree/repo and outside .git; readonly-pipeline validates a shell pipeline; rm-destructive detects destructive recursive removal. Their descriptive “match” strings are not interchangeable with ordinary patterns.

Settings → Permissions → Rules lets you edit or delete the seeded rules, adjust unmatched actions, and inspect asks from the last day in “What interrupts your agents.” Conflict handling can keep both rules, replace conflicting ones, or add exceptions; runtime precedence still decides overlaps. Activity combines stored timestamps with changes recorded by the screen; it is not a complete permanent audit of every tool call.

03 / Presets

Starting sets, with every seeded rule accounted for

New stores start at Autonomous. Choosing a preset replaces the remaining preset-sourced rules and changes unmatched behavior. Your user rules, learned rules and saved actions stay. An edited preset rule is user-owned, so it stays too. Reset is different: it clears user/learned rules, saved actions and approval counts, then reseeds the current preset.

Common block R · 4 allows

Routine work

  • read / tracked / allow — a file git tracks in worktree or repo root.
  • bash / check / allow — exactly a repository checks command.
  • bash / git-readonly / allow — validated git status, diff, log or show.
  • bash / readonly-pipeline / allow — audited read-only commands; restrictions still apply.
Common block E · 24 allows

Everyday programs

aws · uv · pytest · python · npm · pnpm · yarn · docker · cargo · go · make · gh

For each program, two bash rules: exact "program" → allow and prefix "program " → allow (trailing space). These are command allowances, not a promise that those programs are read-only.

Common block C · 7 denies

Credential patterns

All use glob and decision deny:

  • read ~/.ssh*
  • read ~/.aws*
  • read ~/.gnupg*
  • read */.brindle/daemon.json*
  • bash *daemon.json*
  • read */.env*
  • read .env*
Common block D · 2 denies

Destructive operations

bash / git-force / deny: git force flags or a push that forces or deletes a branch.

bash / rm-destructive / deny: recursive rm of root, a top-level absolute folder, home, current/parent directory forms, or --no-preserve-root. This does not mean every rm is denied.

Common block L · 2 asks

bash / push / * → release and * → release/*, both ask with life: once. Every preset includes them. A saved allow cannot settle them.

04 / Commands

“Read-only” is a checked route through rules

The read-only pipeline matcher is a seeded allow you can remove. It accepts audited programs in non-writing forms, checks all parts, and refuses that allow route if a bash ask/deny covers the command or a part, or a read deny covers files it may read.

Eligible shape
git status
cat README.md | head -20
grep -n "permission" README.md

These can use the routine allow when their arguments pass validation and the current policy does not restrict them. Quoted literal search text is understood as shell words.

Needs further evaluation
sort --output result.txt input.txt
find . -exec command {} \;
cat README.md > result.txt

Writing options, executable actions and file redirection do not get the read-only allow. Other rules and unmatched behavior still decide the result; failing this matcher does not itself mean deny.

Parse shell→Audit every program & option→Check bash restrictions→Check read-denied paths→Eligible allow
  • It supports safe parts joined by &&, ;, | or ||. It excludes substitutions, subshells, heredocs, input/file redirection and unquoted tilde expansion. A program spelled with a path, such as ./cat, is not treated as the audited program.
  • Examples of audited programs include grep/rg, ls, cat, head/tail, wc, sort, diff, jq, checksums, and name/metadata tools. Special checks cover sed scripts, find actions, tee operands and hostname operands. rg --pre, sort -o, yq -i and executable fd options do not qualify. Git validates cwd/options as well as the subcommand.
  • Read checks expand path globs (including dotfiles), inspect option values and scan recursive search trees up to a bounded walk budget. A denied file, unsupported pattern or uninspectable tree withholds the pipeline allow. Name-only programs such as ls do not read file contents and skip that content-deny check.
Ordinary bash allows and compound commands

An ordinary bash allow only matches a simple command containing letters, digits, spaces and _-./:=@%+,. Quotes, wildcards, substitutions and operators prevent a whole-command ordinary allow. A supported compound joined by &&, ; or | may run if rules allow every parsed part. Provider profile handling has additional part-by-part logic, including a safe cd inside a worktree. Denies and explicit asks still take priority.

Unsupported shell syntax produces an explicit “shell syntax cannot be checked safely” ask when an active bash restriction might apply. The restriction parser also checks inner substitution commands. A narrow exception exists for a whole double-quoted substitution used as a git commit/tag message option; the inner commands and possible restrictions are still checked. With no applicable restriction, uncovered commands follow unmatched behavior, including Autonomous’s allow.

These are tool permissions, not an operating-system sandbox. File-read denies are checked by file tools and by the audited read-only route. They do not prove that an otherwise allowed Python, shell or network program cannot access a file. The everyday program rules are broad. Provider sandboxes, profile file scopes and other guardrails are additional layers with their own limits.

05 / The Inbox

Exact requests become useful decisions

A pending ask retains its exact request, then proposes a broader general form. Active held requests are grouped by repository + kind + general pattern, across sessions. The oldest request supplies the group’s scope ladder. A group displays a deny if any member is blocked; otherwise it displays the tightest approval lifetime.

Two workers, one Inbox item

feature-b → main @ origin
* → main @ origin

The real Inbox starts at the general rung if it fits the displayed limit, or the first fitting rung. “Narrow to this request” selects the oldest exact request where an exact rung exists. At exact scope, Allow once / Deny answers that oldest request alone; at wider scope it answers the item. A push allow must cover every push and allow any non-push parts alongside it; a push deny only needs one possibly matching push.

06 / Saved actions

Remember an answer, keep checking the policy

Held ask→Choose scope + lifetime→Save→Answer eligible holds→Recheck on use

Which answers persist?

ChoiceStored result
Allow onceNo saved action; allow the selected held requests.
This sessionAllow bound to the root session, shared by its workers.
TimedAllow until approval time + chosen minutes.
Always allowAllow until deleted, within current policy limits.
DenyNo saved action; stop the selected held requests.
Always denySaved deny until deleted.

What a saved action contains

id · kind · pattern · decision · scope · level · request · life · minutes · expires · session · repo · created · note

It retains the exact originating request as well as the scope pattern. All-repository scope stores no repo restriction; other scopes retain the group’s repository. Older migrated records may also carry identity/repository/remote bindings and a use budget.

The grant is saved before held requests are answered. If a worker’s hold has ended, answering can fail while the saved action remains. Responses distinguish resumed, stopped, skipped and failed requests.

Saving does not weaken the rules. A deny rule wins before any saved allow. A saved allow must fit all current ask limits and the current organization policy each time it is considered. A saved deny is checked before automatic allows. Expired actions are ignored, not automatically erased.

Settings → Permissions → Saved actions opens an editor for scope, decision and lifetime, or lets you delete with undo. For supported kinds, “A specific target inside the current scope” narrows the pattern. Editing a timed action starts its duration again from the save; its creation timestamp stays. A session action requires a session identity. Deleting an action removes its future effect; it does not undo an operation already run.

A broad bash grant is not permission to smuggle arbitrary syntax through a command family: non-simple commands normally need an exact saved pattern. The explicit repository-wide * scope covers all commands. A later rule or organization limit can make an existing saved allow unusable without deleting it.

Learning is a separate path

Claude requests left to a person can be paired with a successful PostToolUse by tool and input. Two approvals of the same learnable exact pattern make a suggestion. Nothing turns into a learned rule automatically: the person must accept it. Codex has no matching tool-use identity here and does not contribute this approval learning. Saved actions are the explicit Inbox decisions described above.

07 / Unblocking work

“Allow all” makes a bounded plan

Allow everything waiting

  1. Build one group per repository, kind and general form.
  2. Try the general scope with the group’s permitted lifetime: timed at its cap, forever when permitted, otherwise session.
  3. For each request that cannot use that plan, try its exact scope and own permitted lifetime.
  4. Leave denied or ineligible requests waiting. Save grants, then answer each eligible live hold.

“Always allow” requests forever; it does not silently shorten a forbidden forever approval. The plan reports grants, request counts and skipped items. Once-only release asks remain waiting for individual one-time approval.

Add exceptions for blocked asks

  1. Find the currently denied waiting requests.
  2. Add an exact exclusion to each blocking deny that lives in the person’s store.
  3. Leave external denies locked: repository, profile or organization rules cannot be narrowed here.
  4. Re-evaluate. If unmatched-deny still blocks it, add an ask rule for the general form.
  5. Apply the allow-all planner to the now-eligible requests.

This changes policy as well as granting approvals. An exception removes a match from a deny; it does not override other denies. Results include exception/addition counts, locked requests and failures.

08 / Enforcement

One engine, five different execution paths

The shared answer only matters where an adapter invokes and enforces it. Provider permission modes, profile allowed_tools, file guardrails and native permissions still matter. A shared allow is not a universal bypass of those layers.

Claude Code

PreToolUse + PermissionRequest

PreToolUse checks plan-first/file guardrails, then shared policy when on. It returns denies and forces explicit asks before profile bash allowances. A shared allow or unmatched ask leaves the rest of that hook and Claude’s own permissions to act.

When Claude raises PermissionRequest, shared policy can allow, deny, or hold an ask for the app. If no app answer arrives, Claude’s own prompt remains. Claude asks can be recorded and held with the shared policy off too.

A tool that Claude runs without PermissionRequest does not receive that hook’s shared allow evaluation. Successful asked tools feed the separate approval-learning path.

Codex

Trusted PermissionRequest hook

brindle passes its hook in session flags only after trust is verified in the actual Codex home. New or changed brindle hooks are trusted automatically when policy is on; deliberately removed trust stays removed.

Structured shell and patch requests go through shared rules plus profile denies and bash allows. A multi-file patch must be accounted for and all requests decided. A single ask can be held in the app; multi-request asks fall back to Codex. Explicit asks beat profile bash allowances.

With no trusted hook, Codex uses its own approvals and brindle warns. A dontAsk profile refuses uncovered requests in its fallback path. Policy-off reviewers may use an already trusted hook for their profile allowlist.

Antigravity

PreToolUse · two modes

agy_approvals: "brindle" is the default for agents brindle runs. It launches with --dangerously-skip-permissions, so the strict hook must return allow or deny, never ask. This enforcement runs even with permission_policy off.

Rules and profile bash allows decide first. For an unmatched ask, validated workspace/artifact files, certain own-instruction reads, brindle MCP and conversation-only tools can qualify. Explicit asks block these fallback allowances. Ambiguous paths are refused. Unresolved asks can be held in the app, then refused and, where appropriate, escalated to a supervisor.

In "prompt" mode agy ignores a hook’s allow. Safe, expressible rules are mirrored into agy settings; asks, overlapping allows and rules that cannot be expressed without widening are omitted. The person answers agy’s own prompt.

OpenCode

tool.execute.before plugin

With policy on, the plugin evaluates supported tools before execution and throws on a deny. An explicit ask is converted to deny because this shared-policy path cannot hold the call for a person. Other shared allows and unmatched asks leave OpenCode’s own configuration to decide.

Profile permissions are translated into OpenCode config. There is a narrow exception for scoped read-only git: validation can authorize the exact call and the plugin answers that permission once. This validation exists with policy off too.

General OpenCode approval prompts are answered in its pane, rather than through grouped held asks. A saved allow does not generically override OpenCode’s own prompt.

Native

Dispatch before tool execution

When on, shared policy is checked with workspace and root-session identity before the profile’s own permissions. Denies, explicit asks, decisions on ask rules, and user/learned-rule allows are returned to dispatch.

Preset allows and unmatched asks defer to the profile. In this branch, a saved allow for an unmatched ask has no attached rule and also defers; a saved allow settling an explicit ask is returned. The profile’s own read/command rules still govern the deferred path.

A request requiring a person is held through the daemon. Native has no terminal approval prompt; no app answer means refusal. With policy off, the shared callback defers to the profile.

The app hold is an active channel

A hook registers a unique holder with the daemon, then records request identity and a digest of its exact input/suggestions. Inbox answers go to that holder; a database row alone is never an authorization.

The default hold is one day. It ends on an answer, terminal handoff, closure/pause, the CLI moving past the prompt, daemon loss, or expiry. Claude/Codex can fall back to their own prompt; strict agy/native refuse without an answer. Codex caps a longer configured hold to its hook’s fixed allowance.

09 / Upgrading from 0.4.7

Old choices are translated, not silently widened

The current store format is version 3. A store without a preset is migrated on load. A newer unsupported store is read with blocking denies and is never rewritten by this engine. Unsupported rule rows are preserved: an unreadable allow of a known kind is ignored; other unreadable rows block their kind, or every kind if the kind is unknown.

Old store / choiceCurrent resultHow it is recognized
Version 1, before presetsStandardPreserves own/learned rules and approval counts.
0.4.7 StrictSecureRepo-scoped * glob asks for all seven kinds.
0.4.7 BalancedStandardSame shape, with read/write/edit allowed and other kinds asking.
0.4.7 LenientPermissiveAll kinds allowed except mcp/other asking.
0.4.7, no recognized editor presetAutonomousVersion 2 fallback; distinct from version 1.

If repositories had different recognized presets, migration chooses the strictest: Secure → Standard → Permissive. Recognized editor seed rows are replaced by the new seed; other rules stay. Raw old rules remain under v2_rules, and old remembered data is preserved.

Remembered push approvals

Old branch becomes current destination / general (any source into that destination), remote stays remote, repo becomes repository, and all stays all.

Migration retains the approving owner, git directory and remote URL bindings where required, session or timed expiry, and remaining uses (max_uses − uses_spent). Bindings are checked again on use.

Remembered .env reads

Become exact saved read allows, with their original reach and bindings. A saved allow still cannot bypass a current credential deny: edit the blocking policy if that access is intended.

Expired, exhausted, unbound or unexpressible remembered grants do not become active saved allows. Old expires_at on rules is read as expires.

10 / Organization limits

A saved allow must fit the organization today

For Team organizations, the policy’s permission_grants block bounds saved allows. Without a Team organization there is no extra organization ceiling here. For a Team member, an unreadable policy, a paused/blocked member, a missing grants block, or allow: false means no saved allow applies.

Action kinds

kinds must include the request kind. A saved push is checked against the organization’s bash kind. Organization deny specs are added to the shared rule set.

Duration

The lifetime must be in lifetimes. Timed approvals must be at most max_minutes. Forever additionally requires allow_persistent.

Reach

Exact/general/destination/branch map to org branch; remote → remote; repository/server → repo; all → all. The required scope must be allowed.

The engine reads these limits when granting and again when considering a saved allow. The displayed options are not a substitute for server validation. “Allow once” does not create a saved grant and skips saved-grant ceilings, but it still cannot approve a request whose policy is deny. Saved denies do not need organization approval ceilings.

Roles and remote lists are not local-rule fields. This checkout’s local permission editor does not implement the preview’s per-rule role picker or per-rule allowed remote URL list. Organization role/policy management is separate; migrated push grants can retain exact remote-URL bindings. Do not infer that a broad local grant is constrained by an unimplemented preview field.

11 / The policy switch

The selected preset and the active switch are separate

{ "permission_policy": "on" }

load_repo_config takes an explicit setting from local config, then shared repo config, then user config. With no explicit setting, it defaults on when the license has learned_rules (Pro and up), otherwise off; license errors default off. The dataclass starts at off. Shared-policy adapters check for the exact value "on".

On

Invoke shared policy where supported

Hooks/adapters consult current rules and saved actions, with the provider limitations described above. Choosing Autonomous changes uncovered behavior inside that engine; it does not guarantee every provider runs every tool automatically.

Off

Provider and profile permissions remain

The general shared checks are bypassed for Claude/Codex/OpenCode/native. Claude still records/holds its own permission prompts. Codex reviewers may get a previously trusted hook for their allowlist. OpenCode still validates scoped read-only git. Strict agy still enforces shared rules regardless of this switch.

Turning it off does not delete the store, presets or saved actions, and does not disable plan-first checks or profile guardrails. Some integration is installed at launch (Codex hook flags, OpenCode’s policy environment, agy hooks/mode); a config edit cannot retroactively add launch flags to an existing process. Check a fresh launch when changing enforcement configuration.

12 / When behavior surprises you

Start with the request, the rule, and the provider

My worker is stuck on a prompt

Open Inbox and check whether the request is held for the app or requires its provider’s pane. A live app hold can be answered there or handed to the terminal. OpenCode’s general prompts and agy prompt mode use the pane. Native and strict agy have no independent approval prompt: without a live hold answer, the call is refused. Check the reported reason and the worker’s current provider/profile before adding rules.

I chose Autonomous. Why does it still stop?

Credential and destructive denies, default-branch asks, and once-only release asks are seeded even there. User/learned rules survive preset changes. Repo, profile and organization denies can add restrictions. Shell syntax may produce a bound ask. A provider or native profile may still require its own approval after the shared engine allows a call.

I added an exact allow, but a broad rule keeps winning

Specificity is not precedence. Inspect active denies, asks and saved denies, including restrictions on a part of a shell command. Edit the stronger rule or add an appropriate exception where you own it. The Settings conflict editor offers keep, replace or exception handling. A local allow cannot override an external deny.

I approved this before. Why is it asking again?

Allow once saves nothing. Check Saved actions for scope, repository, lifetime, expiry and session. Editing a policy or changing organization limits may invalidate a saved allow. Release push asks always require one-time approval. Migrated grants also check owner/git-directory/remote URL bindings and remaining uses. For non-simple shell commands, a family pattern usually does not cover the command.

Why did “Narrow to this request” answer only one worker?

At exact scope, Allow once and Deny answer the group’s oldest request only. A wider scope answers the item. A saved decision searches all covered pending requests, checking each one’s policy. MCP already starts with one tool and has no separate exact rung.

Why did Allow all leave some workers waiting?

Its plan cannot override deny rules, save a once-only approval, or exceed any request’s own or organization limits. “Always allow” requires forever eligibility. Inspect skipped/locked/failed results. A hold that ended while the plan was applied can fail to answer even though the grant was saved.

It is just a read-only command. Why does it ask?

Look for a bash ask/deny, a protected file reached by arguments or recursive search, a writing/executable option, a path-spelled program, or syntax outside the audited route. Secure intentionally omits the pipeline allow and seeds a broad bash ask. A read-only matcher failing means other rules or unmatched handling decide, not that the tool was classified as destructive.

Codex never reaches the app’s permission Inbox

Check the launch warning and hook trust in the Codex home brindle actually uses. New/changed hooks are normally trusted automatically; removed trust is respected. The person can restore it with brindle permissions install-codex-hook --yes. An old/unsupported Codex may not accept hooks. Multi-request patch asks also fall back to Codex rather than the single-request app hold.

A saved allow did not bypass OpenCode or native permissions

OpenCode’s general policy path only vetoes; its own permission config still decides an allow. Native defers preset allows and unmatched-ask saved allows without a rule to its profile permissions. A saved allow settling an explicit ask is handled differently. These are adapter behavior, not evidence that the saved action disappeared.

I turned the policy off, but permissions still apply

Off does not mean unrestricted. Profile permissions, Claude plan/file checks, OpenCode’s scoped git validation, and strict agy enforcement remain. Confirm which config wins (local → shared → user), and whether the process was launched with the intended integration flags.

Source notes / Guide comparison

Where the code differs from the shorter guide

This file follows permissions-guide.html for its 880px reading column, Geist font stacks, type scale, rounded diagram surfaces and exact light/dark palette. It follows the implementation for behavior. These are the verified disagreements with that guide:

  1. Decision order. The guide puts saved allows, allow rules and read-only commands before ask rules, and says the first match decides. The engine gives deny precedence over ask, then allow, then unmatched. Saved denies precede automatic allows; saved allows settle asks only within all current limits. Source groups are not independent first-match stages.
  2. Read-only commands. The guide says they always run, even with syntax brindle cannot fully parse. The code validates syntax, programs, options, restrictions and potential denied reads. The pipeline allow is removable and absent from Secure; Secure’s broad bash ask also beats its routine git/check allows.
  3. Read and command rows. The matrix says all file reads run and Standard commands ask. Only tracked reads are routinely allowed in every preset; Permissive adds worktree reads, Standard asks for other uncovered reads, and Secure denies them. Standard and Permissive seed everyday-program allows, so command behavior is not a single blanket ask/run cell. Credential denies remain.
  4. Secure pushes and tools. The matrix labels pushes “owners only” and all web/connected tools as 15-minute asks. The local seed has no owner gate: bash pushes ask within the applicable limits. Fetch asks for up to 15 minutes; uncovered MCP/other requests fall to deny.
  5. Default branch versus release. The guide combines “main or release/*” as once-only for Autonomous. The code asks for @default (not necessarily main) and permits Autonomous saved approvals up to all/forever. Pushes into release and release/* ask once in every preset and cannot be settled by saved allows.
  6. “Every cell is an ordinary rule.” Unmatched handling is a store setting, not a seeded rule. Several cells describe a combination of rules and fallback. “Deleting repos” is also broader than the actual destructive-rm matcher, which checks specific recursive targets and flags rather than every repository deletion.
  7. Organization tier. The guide says Enterprise only. The saved-grant ceilings and organization denies here are read from Team organization policy. Local rule rows have no role field; organization role assignment is separate.
  8. Inbox and Activity guarantees. A saved allow does not universally make a request disappear into an Activity “resumed” entry: it must pass current limits and provider enforcement. Grouping includes repository, kind and general pattern; MCP defaults to one tool, not an entire server. The Settings Activity tab shows policy/saved timestamps and screen changes, not a complete execution log. Providers record permission history selectively.
  9. The on/off switch. The guide says on by default and that off delegates everything to the CLI. Without an explicit setting, code defaults on only with the learned-rules license capability and off otherwise. Strict agy still enforces policy when off; native has no separate CLI prompt, and other profile/hook protections remain. The config loader contains no temporary “turn back on after merge” behavior.
  10. No built-in rules. Editable preset seeds replace the normal defaults, but the engine still synthesizes safety decisions such as the shell-syntax ask and blocking rules for unreadable policy. They are not ordinary removable preset rows.

The separate permissions preview also shows per-rule role and allowed-remote-URL controls that the local Rule schema/editor do not implement. Source links throughout this explainer identify the implementation behind each correction; they are relative conveniences for a checkout. The explainer itself works offline as a standalone file.
