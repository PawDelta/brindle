Building the in-app visualizer

Six workers in three waves. The engine, the sandbox and the reader start together against one contract (below). The sandbox gates the ship: no visual renders for anyone until hostile probe pages make zero requests on every webview we ship. Visuals are off by default. With them off, brindle offers a small Make a visual? only when a decision clears hard rules and a rate limit.

3 · decision e: off by default, a discerning offer

“Make a visual?” shows only when a decision clears the rules

Ship the one-approval release flowa3c91e07 3 options × 4 trade-offsbrindle can show this choice as a visual
supervisor › Three release flows fit. A: tag first … B: gate on CI … C: two approvals … Which should 0.6.2 use? Reply A, B or C.

The agent asks in text as it always does. The offer adds to the text and never blocks it. Clicking it delivers “The person asked for a visual of: <question>” and allows one publish_visual. The chip is a native <button> (with a sibling × Not now button) in the header's Tab order, so it works from the keyboard. It never takes focus on arrival. A separate role="status" line announces it, and the chip appears 2 s after your last key in the chat. Its label is brindle's own wording built from the tool's counts, never agent prose.

VisualsLet agents show decisions as pages in the app. While this is off, brindle offers one only when a choice is hard to read in the terminal.

The setting lives in Settings › General and is stored in ~/.brindle/config.json as visuals: "off" | "on", next to claude_permission_mode. When it's on, agents publish directly under the same “when” rules below, and only the cooldown applies. Planning docs aren't gated by it (Q3).

Offer when all of

  • The agent is about to ask the person to choose (not to approve a go-ahead).
  • And one of these holds:
    • options: ≥3 options, or 2 that differ on ≥3 attributes
    • comparison: a table ≥4 rows × ≥3 columns
    • flow: an order, pipeline or dependency with ≥5 steps or a branch
    • diff: a before/after longer than ~12 lines
    • layout: any UI or visual choice (always: a terminal can't show it)

The agent passes kind and the counts. The engine refuses an offer below these thresholds, so the agent has to state why.

Never offer for

  • Yes/no, “go ahead?”, or anything answerable in ≤3 short lines
  • Status reports and summaries with no decision
  • Permission asks and plan approvals (they have their own cards)
  • A worker's question to its supervisor (an offer is for the person)
  • A question the person already answered in chat

Rate limit engine-enforced, per session

  1. At most 1 open offer; a second is refused while one is showing
  2. 15 min between offers; 4 a day
  3. The same question (normalised hash) is never offered twice
  4. 2 dismissals in a row stop offers for that session for 24 h, or until you accept one
  5. An offer folds silently after 30 min or once you answer in chat

A refused offer_visual returns {offered:false, reason} at once, so the agent never waits on it.

5 · key decisions, alternatives, and my challenge to each

Where I'd push back before we build

D1The reader replaces the chat (a)

Alts
The concept's side panel; a third tab next to chat and shell.
Challenge
You lose the agent's surrounding text while you answer, and a mid-task terminal hidden from view can wedge on a prompt you don't see. Esc inside the frame is invisible to the host.
Do
Keep the PTY mounted (hidden, not unmounted). The answer bar carries the question text and a note field. A sap edge-badge on Back shows when the agent asks something new. The injected snippet forwards Esc (a spoofed Esc only closes the reader).

D2Rail + Focus (b)

Alts
Keep the full sidebar; hide it fully with no rail.
Challenge
Two collapsed states are two layouts to keep working. A rail with no Inbox count is worse than none.
Do
One sidebarMode state (full / rail / hidden) in App.tsx. The rail is a render mode of Sidebar.tsx, not a new component. Rail by default.

D3Who judges “hard to read” (e)

Alts
The engine parses the agent's terminal text for option lists; or the agent decides freely.
Challenge
Parsing a TUI's output is brittle across providers. A free agent over-offers, because LLMs like making things.
Do
The agent declares kind + counts; the engine checks the thresholds and the rate limit. It's self-reported, but cheap to refuse and impossible to spam past the limiter.

D4Off by default (e)

Alts
On by default; off with no offers.
Challenge
Off by default means most people never meet the feature unless offers fire, so the limiter's thresholds decide whether it exists at all. Too strict and it's dead code.
Do
Log offer / accept / dismiss counts in the debug log (no content). Tune the thresholds after a week of the owner's use before release.

D5iframe in the app's webview (i)

Alts
A separate child webview per visual (Tauri add_child, behind an unstable feature).
Challenge
A sandboxed frame usually shares the app's web process and main thread, so a while(true) in a visual freezes the whole app. The daemon and sessions survive; the window doesn't.
Do
Use the iframe for v1. Before mounting, set a “mounting v_x” flag that the frame's first pong clears. If the app restarts with the flag still set, that visual opens as “froze last time · open anyway?”. Revisit the child webview if it happens in practice (Q8).

D6No keep prompt on remove (d)

Alts
The concept's keep list in the remove dialog; a passive count line.
Challenge
The prompt was the concept's only safety net. Without it, a visual you meant to keep is gone with no undo.
Do
As decided: no prompt, Keep in the reader. Optionally the existing remove confirm's sentence says “and its 3 visuals (1 kept)”, a count with no checkboxes (Q2).

D7What gets exported (h)

Alts
The raw HTML file; a PDF; a Word file from the Pro server's renderer.
Challenge
Neither Drive nor SharePoint will run a visual's script. Raw HTML exports a JS-built page as blank, and on SharePoint it's a file that runs scripts in the recipient's browser. There's no local PDF or Word renderer (no dependency in pyproject.toml).
Do
Export the rendered DOM: the injected snippet posts outerHTML, and the daemon allowlist-sanitises it (no script, no on*, no URLs other than data:), stamps the answer and runs the secret scan. Google converts it to a Google Doc; SharePoint gets .html. Plans: Google converts the markdown; SharePoint gets .md (Q4).

D8Export rides the Pro docs path (h)

Alts
A separate, non-Pro sign-in with brindle's own OAuth client ids.
Challenge
The client ids and the export_destinations policy come from the Pro server (docs_api), so a Free user's Export shows Download only. “The same mechanism” brings that limit with it.
Do
Reuse it as is. Download (.html / .md) works everywhere. Ask the owner whether Free should get Drive (Q5).
