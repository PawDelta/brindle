1 · milestones

Milestones for goals with forty of them

A typical goal has 30 to 50 milestones. This one has 40: 28 passed, 1 running, 1 with a failing check and 10 upcoming, in four phases. Only what needs a look is open, and everything else folds into one quiet line. Three variations of the same calm approach, each drawn in the sidebar and the session panel. Switch to the 5-milestone goal to see the same design on a short goal.

  1. barOne segment per milestone. Hover for its title, click to jump to it.
  2. openOnly the running milestone, the failing one and the next one or two.
  3. foldedPassed fold into “✓ 28 passed”, the rest into “○ 8 more upcoming”.
  4. past 15Filter chips and search appear once a goal has more than 15.
  5. sidebarThe bar, what's running, and a chip when a check is failing.

2 · slow buttons

Dim after 300 ms, with the motion outside the button

Every button below is live: click it. Nothing changes for the first 300 ms, so a fast answer never flickers. Past that the button dims to 55% and keeps its label and size, and the motion happens around it, never inside it. With reduced motion, each variant shows a still mark instead.

Try 200 ms: nothing should appear.
0–300 mspressed, unchanged
≥ 300 msbutton dims to 55%, indicator fades in around it (200 ms)
answerindicator fades out, button returns; a failure shows under the button as today
3 · two proposed learned rules

What each rule would change

Both rules come from repeated review findings about cleanup code. Each card shows the failure as it happened, the same moment with the rule followed, and what the rule costs.

801c9de5clear triggerfound 3 times
Re-check state right before any kill, stop, delete or reap; skip if it changed.
before · cleanup acts on a plan made earlier
after · one look at the state, right before acting
Stops a known bug, found 3 timesNo more killing a worker, or deleting a worktree, that turned busy or dirty after the cleanup was planned.
One extra test per cleanup fixEach fix needs a test where the state changes between planning and acting.
tests per fix+1 diff width1 call review rounds±0
17d7c3aevague triggerfixed-in-one-place bugs
When you add a guard to shared state, apply it to every path that reads that state.
before · a fix guards one reader of the state
after · every reader gets the guard, in one change
Catches fixed-in-one-place bugsThe same bug can't come back through a path the first fix didn't touch.
Vague, and costly"Every path that reads it" has no clear edge, so diffs get wider and reviews take more rounds while people argue the scope.
tests per fix+1 per path diff width2–3× review rounds+1–2
suggestionAdopt 801c9de5 as written. Its trigger is a concrete call (kill, stop, delete, reap) and its cost is one test. Hold 17d7c3ae until it names its scope, for example "every caller of the function you guarded, found with graphify". Then it would be checkable, not a matter of judgment.
