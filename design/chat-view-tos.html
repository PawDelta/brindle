What the provider terms allow for the chat view

Each option in the chat view plan checked against each provider's published terms, for each way of signing in. Every verdict links to the clause it rests on. Wording I couldn't read myself is marked unverified.

All pages read 2026-11-06 Covers plan options A, B (and B′, the Agent SDK) and C Branch docs/chat-view-tos-check

Not legal advice. This is an engineering reading of public terms, to steer the design. Before anything ships, a lawyer should confirm it, or the provider should in writing.

02 · Four things to flag

Transcripts, automation, branding, and other brindle users

1 · Reading local transcripts Partly inferred

Nothing I read forbids a person's own software from reading files the CLI writes on their own machine. That absence is evidence, not permission. For Claude, the carve-out for the user's own subscription in the unmodified binary makes it a reasonable reading. For OpenAI (the consumer Terms' extraction clause for a ChatGPT login; the Services Agreement's §3.3(f) for an API key) and Google (“third party software … to access the Service”), whether the clause reaches local files isn't established, so those are inferences. Either way, the risk is in what sits next to those files:

  • Never open the credential files: Claude's credential store, ~/.codex/auth.json, or Antigravity's OAuth token. Anthropic bars developers who “collect, store, or intermediate” session tokens; OpenAI says to treat auth.json “like a password”; Antigravity's example of a breach is OAuth reuse.
  • Mask before anything leaves the daemon (already in the plan).
  • The transcript format isn't a contract. That's an engineering risk, not a legal one.

2 · Automating the CLI Unclear on subscriptions

Anthropic's Consumer Terms bar access “through automated or non-human means, whether through a bot, script, or otherwise”, except via an API key “or where we otherwise explicitly permit it” (§3, item 7). The Claude Code page explicitly permits an end user “signing in to the unmodified Claude Code binary with their own Claude subscription, including where a platform hosts Claude Code”. It doesn't say whether a supervisor agent driving that pane counts as automated access.

This question covers brindle today, not just the chat view: workers on a subscription are already driven by a supervisor. B on a subscription makes it sharper. OpenAI documents ChatGPT-managed auth for CI as an advanced path for “your Codex account”, and recommends API keys for automation. Google's clause 6 is the strictest of the three.

3 · Rebranding With conditions

  • Allowed: plain, accurate text such as “runs Claude Code”, or model names as labels.
  • Not allowed: “you can't use the Claude Code or Anthropic names or logos as part of your own product, feature, or company name” (Legal and compliance). The SDK guidelines forbid “Claude Code” and “Claude Code Agent”, and “visual elements that mimic Claude Code”. They allow “Claude Agent” and “{YourAgentName} Powered by Claude”.
  • So: call it “Conversation” or “Chat”, never “Claude Code chat”, and don't copy the TUI's look. I didn't read OpenAI's or Google's trademark guidelines. unverified

4 · Offering it to other brindle users With conditions

brindle ships to other people, with paid tiers. What the terms require depends on the route:

  • Claude Code inside brindle (A, B): “preinstalling or running Claude Code in your products or services” requires the Commercial Terms, an unmodified binary with no built-in sign-in method removed (including Claude account sign-in in the pane), and “Customers may not pay for, resell, or intermediate Claude usage on their end users' behalf.” So for Claude Code sessions, each person brings their own key, plan or cloud credential.
  • brindle's native loop on the API (C): that Claude Code rule doesn't apply. Commercial Terms A.1 permits powering “products and services Customer makes available to its own customers and end users”. The reviewer reports that OpenAI's Services Agreement §2.2 does the same; I couldn't read it (403). brindle could fund usage on its own key here. The limits are D.4's ban on reselling the Services “except as expressly approved” and the equivalent clauses.
  • OpenRouter: no “reselling API access to Models” (§7, item 4). Building it into your own product is allowed (§5.1).
  • Gemini API: users 18+, available regions, Paid Services for EEA users.
  • The Usage Policy's rule to disclose AI applies to agents talking to external users, which brindle's people aren't.

Users bringing their own keys everywhere is my product recommendation (simpler billing, no reseller questions). It's not something every provider requires.

03 · Bottom line

A looks safe where checked; B and C rest on API keys

A mostly ✓ · B, C keys

Option A (a read-only view from the CLI's own transcript) is allowed with conditions for Claude, on a subscription or an API key, and for Gemini and OpenRouter API keys. The conditions: brindle never touches a credential file, the CLI stays unmodified, and the tab isn't branded as Claude Code. For Codex and for Google logins, A is probably fine, but that's an inference. Three clauses haven't been shown not to reach local transcripts: the consumer Terms of Use extraction clause for a ChatGPT login, the Services Agreement's own §3.3(f) for an OpenAI API key (alongside its §2.2 grant for customer applications), and Google's access clause for a Google login. So those cells stay Unclear. So does every cloud route, because I didn't read the cloud terms. Option B is allowed with conditions on API keys. It is not allowed on a Claude subscription: the Agent SDK path is barred outright, and raw claude -p is high risk. It is not allowed on a ChatGPT login through app-server auth while brindle is a paid product, and not on a Google login. Option C is allowed with conditions on API keys. It is barred on Claude and Google logins. A ChatGPT plan is possible only through Sign in with ChatGPT, which a paid app like brindle must apply for. Users bringing their own credentials is a requirement for Claude Code sessions and a recommendation elsewhere. One open question reaches beyond the chat view: whether a supervisor driving a subscription-logged CLI counts as “automated access” under Anthropic's Consumer Terms.

04 · What the plan must change

Edits to api-key-ui-plan.html

  1. B on Claude: API key or cloud route only, not “API-key users first”.Phase 2 and the recommendation say “API-key users first”. Make it a rule: chat mode refuses to start unless claude_credential() names an API key or a cloud route. Otherwise the session stays in the pane, with a short explanation. In section 04, change B's “Works for subscribers too” score from 3 to 1 for Claude.
  2. B′ (Agent SDK) never runs with a claude.ai login.Add this to G8. The SDK note is explicit, and “unless previously approved” means written approval from Anthropic, not an assumption.
  3. Add a spike gate: credentials stay untouched.Extend G4 so each adapter and runner is shown never to open Claude's credential store, ~/.codex/auth.json or Antigravity's token, and the native client keeps its own User-Agent.
  4. Codex B starts on CODEX_API_KEY.app-server sign-in “has never been permitted for commercial or hosted services”, and brindle's paid tiers make it commercial. Before ChatGPT-plan chat mode (B) or ChatGPT-plan native use (C), submit OpenAI's Sign in with ChatGPT interest form and build on that flow, never on Codex's saved login.
  5. Google stays out of B and C on a Google login, as a rule.The plan already scopes Antigravity out. Write down the reason (clause 6), so it doesn't come back as a “quick win”.
  6. Name and look.“Conversation” or “Chat”, never “Claude Code chat”. Don't reproduce the TUI's visuals. Plain text such as “runs Claude Code” is fine. The mock in the plan already complies.
  7. Distribution.PawDelta should accept Anthropic's Commercial Terms for a product that runs Claude Code. For Claude Code sessions (A, B), the plan must state that each user brings their own key, plan or cloud credential, and brindle never pays for or intermediates that usage. For the native loop (C), funding usage on brindle's own key is permitted under Commercial Terms A.1, subject to the resale limits. Bring-your-own-key there is a product choice. I recommend it, but it isn't required.
  8. Ask before building B on any subscription.Anthropic's legal page points to sales for questions about permitted authentication. Put the automation question (flag 2) to them as well, since it covers brindle today.
  9. Re-check after 2026-11-12.Anthropic's new Usage Policy takes effect then, and adds the “route requests through consumer subscriptions” wording.
05 · What's unverified

Gaps in this check

  • OpenAI Terms of Use and Services Agreement: openai.com returned HTTP 403 to my automated reads, twice. I have wording from an archived 2024-12-11 revision (search snippets) and the reviewer's report on the current versions (both effective 2026-01-01): the Terms of Use keep the Output-extraction clause and send API use to the business terms; the Services Agreement allows customer applications (§2.2) and has its own, qualified extraction restriction (§3.3(f)). Someone needs to read the live pages in a browser.
  • Codex app-server “Authentication modes” (including the chatgptAuthTokens mode) and the Sign in with ChatGPT sub-pages on preview limits and client IDs: not read verbatim. The “Auth endpoints” section is now quoted verbatim. The OpenAI help article on using Codex with a ChatGPT plan returned 403.
  • OpenAI's stance on ChatGPT plans in third-party harnesses: secondary reporting only.
  • Anthropic's 2026 enforcement timeline (January blocking, February docs update, April cut-off for third-party harnesses): secondary reporting only. The current docs wording quoted above is primary.
  • Cloud terms (Bedrock, Vertex AI / Google Cloud, Foundry, Azure OpenAI), Google's base Terms of Service, OpenCode's hosted plans, OpenAI and Google trademark guidelines: not read.
  • OpenRouter §§13–20: only a summary. The claim that model providers are third-party beneficiaries (§20) is unverified.
  • None of the pages I read had a version date except Anthropic's Consumer Terms, Commercial Terms and Usage Policy, Google's Gemini API terms and OpenRouter's terms. The docs pages can change without notice.
